# ADR-022: Central agent asset registry

**Status:** accepted
**Date:** 2026-07-08
**Last-updated:** 2026-11-26

## Context

Adding a new runtime artifact to ABCA today, such as an MCP server, a Cedar policy module, a skill, or a prompt fragment, is a **core-code change plus a CDK deploy**. Artifacts are vendored into the container image (built-in MCP servers, first-party workflows), inlined on the Blueprint construct (Cedar policies), or served from repo-local files (`.mcp.json`, `AGENTS.md`). There is no versioned catalog, no immutability guarantee at a given version, and no audit trail of "which asset versions did this task actually run."

The current arrangement has three costs:

1. **Every new tool, skill, or policy costs a deploy.** Rolling out a new MCP server to N repos takes N Blueprint edits and a CDK deploy. Teams can't publish autonomously.
2. **No pin, no reproducibility.** Because assets aren't versioned, "the tool the agent used on 2026-05-01" can't be reconstructed from the task record.
3. **The vocabulary already anticipates a registry.** [ADR-014](./ADR-014-workflow-driven-tasks.md) and [WORKFLOWS.md](../design/WORKFLOWS.md) already did the following:
   - Coined `registry://kind/name` refs (grammar in [`agent/src/workflow/validator.py`](../../agent/src/workflow/validator.py) `_REGISTRY_REF`).
   - Modeled `agent_config` asset kinds (`mcp_servers`, `skills`, `plugins`, `subagents`, `prompt_fragments`, `cedar_policy_modules`) one-to-one with the vocabulary this ADR needs.
   - Designed a resolver interface as a **drop-in swap**, filesystem-backed today and registry-backed later ([`agent/src/workflow/loader.py:89`](../../agent/src/workflow/loader.py), WORKFLOWS.md §"Registry integration (#246)").
   - Left validator rule 8 as a deferred check. The rule is that every asset ref resolves, builtins today and registry refs when the registry lands.

Issue [#246](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/246) proposes closing this gap with a **central versioned asset registry**. The registry is a catalog of typed artifact records that are immutable at a version. Blueprints pin the records by `registry://kind/name@constraint`, the orchestrator resolves them at task start, and the agent receives them as a resolved bundle. The issue has six acceptance criteria: asset kinds enumerated, publish and resolve with semver and immutability, a blueprint reference of at least one kind, agent E2E for one kind, descriptor validation at publish, and tests and docs.

Two forces shape the decision:

- **Prior art exists at AWS.** [AWS Agent Registry](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/registry.html) is a standalone managed service whose native resource types (MCP servers, agents (A2A), skills, plus custom resources) map directly onto #246's asset-kind list. Its built-in features are governance (approval workflow), audit (CloudTrail), notifications (EventBridge), discovery (hybrid semantic and keyword search), an MCP-native discovery endpoint, and IAM or JWT authorization. It does not commit to **semver constraint resolution**. Records carry a version string and support revisions, but the resolution semantics that WORKFLOWS.md commits to (`^`, `~`, or exact, "highest matching version wins", reject `*` and `latest`) remain an ABCA-side concern. The service moved from the Bedrock AgentCore preview namespace to the standalone `agent-registry` namespace on 2026-08-06. The move changed API endpoints, IAM actions, SDK clients, descriptor shapes, and registry data.
- **Substrate is not the invariant.** The invariants that #246 needs are contract-level. They do not depend on the substrate, which is where the data lives: AWS Agent Registry, or DynamoDB and S3. The invariants are semver grammar, immutability per version, resolve-at-task-start, fail-closed on a missing pin, descriptor validation at publish (which caller-supplied fields cannot bypass), and read-path confidentiality (no inlined credentials, and allowlist redaction on the open read path). ABCA has a precedent for this split. ADR-014's resolver interface deliberately abstracts filesystem versus registry so that the substrate is swappable.

This ADR must respect two adjacent decisions and must not reopen them:

- **[#381](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/381), the ADR↔Persona↔Skill graph.** #381 links ADRs, personas, and skills with bidirectional frontmatter edges in `docs/` and plugin markdown, and a parity linter enforces the edges. Both #246 and #381 mention "skills," but they mean different things. #381 is about *documentation graph consistency*. #246 is a *runtime artifact catalog*. This ADR keeps them separate.
- **[ADR-014](./ADR-014-workflow-driven-tasks.md).** Workflows are the registry's first `capability`-kind consumer. The resolution semantics of the `workflow_ref` field are the model that this ADR generalizes to all asset kinds. Workflows themselves stay filesystem-backed in the MVP, because they already ship and are validated. Migrating them to the registry is a separate follow-up, not part of #246.

## Decision

ABCA gains a **central agent asset registry**, a versioned, platform-managed catalog of runtime artifacts that is immutable per version. Blueprints reference assets via `registry://kind/namespace/name@constraint`. The orchestrator resolves refs at the create-task boundary and stamps the resolved `{kind, id, version}` triples on the task record. The agent receives a resolved bundle alongside the workflow file.

The ADR fixes the **contract**. The substrate ranking below was written to defer the choice to the design PR, with a **preferred direction** and a **documented fallback**. That selection resolved to the preferred substrate, **AWS Agent Registry**, behind the `RegistryClient` seam (sub-decision 8). The implementation landed in [#664](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/pull/664) (catalog) and [#665](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/pull/665) (resolve and load). The ranking, alternatives, and flip-conditions are retained below as the record of *why* Agent Registry was chosen and *when* to fall back to DynamoDB and S3. The falsifiable conditions still govern any future substrate change.

**Status.** This ADR is `accepted`, because #664 and #665 are merged. Issue [#771](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/771) completes the required migration from the former Bedrock AgentCore namespace to the standalone `agent-registry` service namespace. AWS still labels the service Preview.

### Sub-decisions

1. **URI grammar and kinds.** The grammar is `registry://<kind>/<namespace>/<name>@<constraint>`. The MVP kinds are `mcp_server`, `cedar_policy_module`, and `skill`. The schema declares, but does not yet load, `plugin`, `subagent`, `prompt_fragment`, and `capability`. In the ADR-014 vocabulary, `capability` means workflow. This grammar *extends* the shape pre-declared for ADR-014 at [`agent/src/workflow/validator.py`](../../agent/src/workflow/validator.py) `_REGISTRY_REF`. That shape admitted a 2-segment `registry://kind/name` form but not the `@<constraint>` suffix or `_` (snake_case) in the kind segment. The implementation widens that lenient acceptance check and puts the **authoritative, strict grammar** in a dedicated parser that is mirrored byte-for-byte across both languages (`cdk/src/handlers/shared/registry/ref.ts` and `agent/src/registry/ref.py`). `validator.py` remains a lenient pre-flight that admits both forms.

   **Short vs long forms (migration note).** [WORKFLOWS.md](../design/WORKFLOWS.md) illustrates refs in a *short* 2-segment form with no constraint (`registry://prompt/web-research-workflow`, `registry://mcp/web-search-v1`, `registry://skill/research-synthesis-v1`). Those refs are **forward-declarations**. The WORKFLOWS spec explicitly marks `registry://` refs as "declared in the schema now but ignored by the runner until the registry (#246) can resolve them." This ADR's strict grammar is the *long* form: 3 segments (`<kind>/<namespace>/<name>`), snake_case kinds (`mcp_server` instead of `mcp`, `prompt_fragment` instead of `prompt`, and `cedar_policy_module` instead of `cedar`), and a **mandatory** `@<constraint>`. Only the long form resolves. The short form stays **lenient-only**. The pre-flight of `validator.py` accepts it syntactically, so that existing illustrative workflows don't fail validation, but the registry *cannot resolve* it until it is rewritten to the long form. There is no automatic aliasing (`mcp` to `mcp_server`) at resolve time. A ref must be long-form to load. Migrating the WORKFLOWS examples to the long form is doc-only cleanup that is tracked with the workflow and registry integration. It is not a blocker for #246.

2. **Semver, not floating.** The allowed constraints are exact (`1.4.1`), caret (`^1.4.1`), and tilde (`~1.4.1`). Validation rejects `*`, `latest`, `>=`, and bare prerelease modifiers. Resolution selects *the highest semver-comparable version that matches the constraint. Prereleases rank below their base version.*

3. **Immutable per version.** `(kind, namespace, name, version)` is immutable once published. Republish attempts fail with 409 `REGISTRY_VERSION_EXISTS`. Content changes require a new version. Mutable metadata is confined to a lifecycle status field.

4. **Lifecycle status.** The full set, in order, is `draft`, `submitted`, then `approved` or `rejected`, then `deprecated`, then `removed`. `submitted` is the ABCA token. Agent Registry names that state `PENDING_APPROVAL`. It is one state with two names, which is mapped once here and called `submitted` throughout. `approved` is the single canonical "resolvable" token (the service names it `APPROVED`), and it resolves silently. `deprecated` resolves with a warning event on the task record. `submitted`, `draft`, `rejected`, and `removed` all fail resolution. See sub-decision 10 for the governance transitions between these states. Immutability of the artifact bytes is a separate matter. Status transitions do not rewrite content.

5. **Resolve at the create-task boundary. The TypeScript orchestrator owns resolution.** Refs resolve in the same place where `workflow_ref` resolves today (`cdk/src/handlers/shared/`). The **orchestrator (TypeScript)** owns catalog lookup and semver selection. It turns each `registry://…@constraint` ref into a fully pinned `{kind, id, version}` triple plus the resolved runtime payload, stamps `resolved_assets: [{kind, id, version}]` on the task record for audit, and passes the runtime bundle into the agent payload. The **Python agent** receives that already-resolved bundle and loads it (sub-decision 6). It does *not* re-run catalog resolution in the normal flow. Python nonetheless carries a mirrored `RegistryClient` and semver resolver (sub-decision 8), which the two-language parity contract and any direct lookup path require. Resolution *authority* at the task boundary still has a single owner, TypeScript, and that single ownership keeps sub-decision 6 (no re-resolution) true.

6. **Fail-closed.** A ref that does not resolve fails admission with `REGISTRY_RESOLUTION_FAILED` and a specific reason (`NO_MATCHING_VERSION`, `REMOVED`, `INVALID_CONSTRAINT`). There is no implicit fallback to a "latest" version. A running task never silently downgrades or substitutes a resolved asset.

7. **Descriptor validation at publish.** Every published asset carries a typed descriptor that is validated at publish. A malformed descriptor rejects the publish. The descriptor lives in the record, and the artifact bytes are separate.

   **Validation must be non-bypassable by any caller-supplied field.** The validated runtime descriptor MUST be carried in a channel **isolated from caller-controlled discovery prose**. The channel is either structurally serialized (not line-oriented text concatenation), or recovered with a parser that is last-wins or rejects duplicate keys, and that escapes every caller-supplied value. A carrier in which a free-text discovery field (for example a skill `description`) can inject or shadow the runtime key defeats this invariant, because it lets a publisher insert a runtime payload that the validator never inspected. This requirement applies equally to `CUSTOM` records. The structural fields of a `CUSTOM` body (including the `custom` flag itself) are validated, not passed through verbatim.

   **MVP.** Validation is delegated to the substrate's **native descriptor types**. MCP records are stored as a protocol-validated `server.json` (schema-checked by Agent Registry). Skills are stored as Markdown frontmatter whose runtime key is emitted and recovered through a real YAML serializer, never by string concatenation, so a newline in a `description` cannot inject a key. Anything without a native type is stored as `CUSTOM`, with verbatim artifact bytes but with its ABCA descriptor fields structurally validated. The MVP kinds therefore get publish-time rejection without ABCA authoring its own schema.

   **Future scope.** The *rich* ABCA capability descriptor originally described here is **not** in the MVP. That descriptor is a cross-kind contract that declares the tools exposed, egress domains, Cedar actions introduced, minimum compute profile, and permissions required. It has a **shared JSON Schema as the single source of truth that both languages consume**, mirroring the workflow-schema decision in ADR-014. The MVP relies only on native and `CUSTOM` shape checks. The shared-schema capability descriptor lands with the capability-descriptor issue ([#481](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/481)).

8. **Resolver interface as the seam.** Both sides of #246, the CDK-side TypeScript orchestrator and the Python agent runtime, call a `RegistryClient` abstraction, not a specific AWS SDK client. This design mirrors ADR-014's filesystem-versus-registry seam. It confined the August 2026 namespace migration to one implementation file per language plus provisioning and IAM wiring.

9. **MVP E2E path is at minimum one asset kind: MCP server.** Per issue AC4, one end-to-end path is sufficient for MVP. MCP server is the primary target because it is the most heavily used asset kind (already vendored built-in in the container) and because Agent Registry has native, protocol-validated support for it. *(Implementation note: #664 and #665 target all three MVP kinds, with a single task that loads an MCP server, a Cedar policy module, and a skill together. That exceeds the one-kind AC4 bar and was verified on a dev stack during review. Cedar and skill hardening continues under the child issues [#478](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/478), [#479](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/479), [#480](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/480), and [#481](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/481).)*

10. **Governance lifecycle is a first-class concern. The MVP interface is deliberately thin.** Publishing follows a lifecycle: **draft, then submitted, then approved or rejected, then deprecated, then removed**. Only `approved` records resolve. Submitted, rejected, and draft records exist but do not resolve. Governance separates a registry from a directory. Deferring the *machinery* entirely would put ABCA in the "partial-match" tier that community catalogs occupy. Choosing Agent Registry as the substrate lets ABCA claim the lifecycle at MVP without building a state machine. The substrate natively provides the state model, the `CreateRegistryRecord → SubmitRegistryRecordForApproval → UpdateRegistryRecordStatus` transitions, CloudTrail control-plane audit, and EventBridge transition notifications.

    **What the ABCA MVP interface exposes (shipped).** The operations are `publish`, `resolve`, `list`, and `show`. Publish creates a record. When the caller holds approver rights and passes `auto_approve`, publish also drives the record through `DRAFT → PENDING_APPROVAL → APPROVED` inline, so that it resolves immediately. Resolvers match only `APPROVED` records. The substrate transition carries rich audit metadata (approver identity, timestamp, `statusReason`).

    **Future scope (not in the ABCA MVP interface).** Three items are deferred. (a) A **standalone endpoint to approve, reject, or deprecate**, so that a normal `submitted` record can be promoted *after* publish without `auto_approve`. Today a record that is not auto-approved stays `PENDING_APPROVAL` from ABCA's side until someone acts on it out-of-band. (b) **Environment-gating** of `auto_approve`, which is approver-*gated* but not restricted to dev environments. (c) First-class **consumption of the substrate's transition events** by an ABCA-side review pipeline. These items are tracked under the lifecycle child issue ([#478](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/478)) and event-governance ([#230](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/230)).

11. **MVP access control, and read-path confidentiality.** There are two Cognito groups. `RegistryPublisher` may publish, which creates a record that awaits approval. `RegistryApprover` may also `auto_approve` on publish, which drives the record to `APPROVED` in one call. Resolve and read are available to any authenticated caller. Standalone promote, reject, and deprecate after publish are future scope (sub-decision 10). **Cedar-governed publish and promote ACLs are Phase 3 ([#480](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/480), [#481](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/481)).** The MVP has no per-namespace ACL granularity. The two-role split is the minimum that makes sub-decision 10's approval workflow meaningful.

    Because resolve and read are open to *any* authenticated caller, two confidentiality invariants bound what the read path may return. **(a) Runtime payloads MUST NOT carry credential material.** Credentials are *referenced* (for example by a Secrets Manager ARN that the orchestrator dereferences at connect time) and never inlined into the stored runtime. **(b) Any read path that a non-approver caller can reach redacts by allowlist.** It projects the known-safe fields for the asset kind and drops everything else. It does not mask a fixed denylist of field names. A denylist over field *names* is fail-open by construction against a payload whose key space is open, because a publisher can attach `api_key`, `env`, or a token in a `url` query string. The allowlist is therefore what makes the redaction fail-closed. Publish-time validation enforces the same closed key set (unknown runtime keys are rejected), so the payload is closed at both the write boundary and the read boundary. The orchestrator connect-path is exempt. It resolves through the `RegistryClient` port, not the human-facing read API, and receives the full payload it needs to connect, with referenced credentials resolved.

12. **Workflows do not migrate to the registry in this ADR.** ADR-014 first-party workflows stay filesystem-backed in the container image. The resolver interface allows a later migration (the vocabulary is aligned one-to-one), but the migration is a separate decision that is not needed to close #246.

13. **Split cleanly from [#381](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/381).** The registry stores skill **runtime artifacts**, which are bundles of prompt and tools that the agent loads at task start. #381's ADR↔Persona↔Skill **documentation graph** stays in `docs/` and plugin markdown, with frontmatter edges and a parity linter. The two must not be conflated. An operator who publishes a skill artifact does not perform the same act as an author who links a skill markdown to an ADR. If a skill record's descriptor eventually cites an ADR, that citation is metadata, not a graph edge that #381 owns.

### Substrate: preferred choice, fallback, and considered alternatives

This section ranks the candidates by fit for ABCA and records the flip-conditions that govern the choice. It was originally written to defer the substrate selection to the design PR, which had to prototype the top-ranked candidate before committing. That selection has since resolved to **option 1, AWS Agent Registry**. The ranking below is retained as the decision record of *why* Agent Registry won and *when* to fall back. It continues to govern any future substrate change.

Among the registry platforms available as of mid-2026, the five requirements that this ADR treats as invariants (publishing, searchable catalog, governance, access control, and support for multiple resource types) leave a small number of viable options. All meaningful candidates remain in preview or early maturity, which reinforces that the `RegistryClient` seam (sub-decision 8) is the hedge that does not depend on a substrate. ABCA should not be locked to any one substrate while the platforms are still changing.

**1. Preferred: [AWS Agent Registry](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/registry.html).** Rationale:

- Native resource types map one-to-one onto MVP kinds: `mcp_server` (MCP protocol-validated), `skill`, `custom` (Cedar module, prompt fragment via caller-defined JSON schema). It has five native types, the broadest coverage of any managed offering in the current field.
- **Governance is a first-class lifecycle.** A record goes from Draft to Pending Approval to Approved or Rejected, with deprecation support. EventBridge notifications and an `UpdateRegistryRecordStatus` API drive the lifecycle, and the API lets external review pipelines (ticketing, security scan, human approval) complete the review programmatically. Auto-approve mode is available for dev environments. This lifecycle matches sub-decision 10 directly.
- Hybrid semantic and keyword search with weighted relevance ranking.
- MCP-native discovery endpoint. An agent can query the registry via MCP without ABCA-specific glue code.
- IAM or JWT (Cognito) authorization. Invoking the registry MCP endpoint with IAM requires `agent-registry:InvokeRegistryMcp` plus `agent-registry:SearchDiscoverableRegistryRecords`. The Cognito groups in sub-decision 11 enforce ABCA's publisher and approver split separately.
- CloudTrail control-plane audit trail.
- Multi-registry organizational scoping. Separate registries per team, environment, or business unit are first-class. ABCA operators would isolate dev catalogs from production catalogs in the same way.
- Managed-service availability remains account- and region-dependent during preview. The deployment gate below lets operators omit the feature where it is unavailable or prohibited.
- AWS-managed. There is nothing new to operate (no MongoDB, no auth server, no self-run gateway). A support contract exists.
- Best fit for an AWS-native platform, which ABCA is by construction.

**2. Fallback: DynamoDB (metadata) and S3 (artifacts).** Use it when the preferred option is blocked. Rationale:

- Matches existing ABCA patterns (`RepoTable`, `attachments-bucket`).
- Full control over semver resolution and immutability semantics, with no gap between what WORKFLOWS.md commits to and what the substrate enforces.
- No preview-status risk. No third-party dependency to trust.
- The cost is extra code to write and maintain (publish handler, resolve handler, IAM grants, descriptor validators, governance state machine, discovery and search). The governance flow in sub-decision 10 is a re-implementation of what Agent Registry provides.

**3. Considered, not adopted for MVP: [mcp-gateway-registry](https://github.com/agentic-community/mcp-gateway-registry) (open-source, Apache-2.0, self-hosted).** It is an Apache-2.0 project that combines a gateway (nginx data plane) and a registry (FastAPI control plane, MongoDB-backed), with native support for MCP servers, A2A agents, skills, and admin-defined custom entities. Federation to AWS Agent Registry, Anthropic MCP Registry, and peer instances is built in. Its publication on the [AWS Open Source Blog (June 2026)](https://aws.amazon.com/blogs/opensource/governing-ai-assets-at-scale-with-mcp-gateway-and-registry/) gives it materially more credibility than the typical community project. It ranks below the preferred and fallback options for ABCA for these reasons:

- **New components to operate.** ABCA is DynamoDB-native. This project introduces MongoDB (or Amazon DocumentDB), a FastAPI service, an nginx proxy, and an auth server. Those are four new components to deploy, patch, monitor, back up, restore, and reason about during an incident. That is a substantial addition for a sample and reference project whose current stack is intentionally small.
- **Scope mismatch.** The gateway and proxy features (per-user 3LO OAuth, virtual MCP servers, gateway-brokered egress) are valuable, but they solve problems that #246 does not ask us to solve in the MVP. Paying the operational cost for capabilities that the MVP does not require is over-scoping.
- **Federation is real, but hedged elsewhere.** The project can federate to AWS Agent Registry and others behind one API, and that ability is architecturally interesting. But sub-decision 8 (the `RegistryClient` interface) already delivers the substrate independence that federation provides. ABCA does not need a second layer of indirection for the same purpose.
- **The governance model is webhook-based**, not a fully integrated lifecycle. Connecting the webhook approval to ABCA's own workflows is additional glue code that we do not need to write.

If the preferred and fallback options are both blocked, or if a future issue explicitly needs the gateway or federation capabilities, this candidate should be re-evaluated then.

**4. Considered and not adopted: [agentregistry.ai (Solo.io)](https://www.solo.io/products/agentregistry).** It is Kubernetes-native and multi-cloud, with four resource types (agents, MCP, skills, prompts) and a full artifact approval mode. It suits Kubernetes-first or multi-cloud platforms best. ABCA is neither. It is single-cloud (AWS), CDK-deployed, and not Kubernetes-first. Adopting this substrate would bring in a Kubernetes-shaped model that ABCA does not use elsewhere.

**5. Considered and not adopted: [Microsoft Entra Agent Registry and Agent Governance Toolkit](https://microsoft.github.io/agent-governance-toolkit/).** It treats agents as first-class identities via Entra Conditional Access, supports 20+ agent types, and provides shift-left CI/CD governance and multi-cloud agent surfacing (including AWS Bedrock). It suits Microsoft-ecosystem platforms best. ABCA has no alignment with Entra or the Microsoft ecosystem. Adopting this substrate would force ABCA to introduce that ecosystem for a single subsystem.

#### Also considered, briefly

The following platforms were reviewed but did not warrant a full write-up above, because each falls short of the invariants that this ADR fixes (typically on governance, resource-type breadth, or fit for an AWS-native platform that is neither Kubernetes-first nor in the Microsoft ecosystem). They are named here so that future readers see that they were weighed and disqualified.

- **[Google Cloud Agent Registry](https://cloud.google.com/agent-registry/overview).** It is GCP-native and launched in preview in April 2026. It supports agents, MCP servers, and endpoints. It is ruled out because it is GCP-only (ABCA is AWS-native), its search is keyword-only (no semantic search), and its governance is IAM-only with no explicit approval workflow.
- **[Smithery](https://smithery.ai/).** It is the largest open MCP server registry (3,000+ servers). It is community-driven and offers SaaS plus a managed gateway. It is ruled out because it relies on a "verified" flag, not on a formal pre-publication review workflow. An October 2025 supply-chain incident illustrated the risk of that model for a governed platform. It is useful as a *discovery* source, not as a governed catalog.
- **[Glama](https://apis.io/providers/glama-ai/).** It is a very large community MCP directory (23,000+ servers). It is ruled out for the same reason as Smithery. It is discovery-only, with no governance.
- **[PulseMCP](https://www.pulsemcp.com/servers).** It is a community MCP directory. It is ruled out because it is a directory, not a registry.
- **[ACI.dev](https://aci.dev/).** It has 600+ integrations, semantic search, and hierarchical access control. It is ruled out because it is a tool-calling platform, not a governed registry. It has no submit, review, and approve workflow, and agents are not first-class resources.
- **[Composio](https://composio.dev/).** It has 1,000+ toolkits, 20,000+ tools, and granular per-user OAuth. It is ruled out because, like ACI.dev, it is a tool-calling catalog with no governance workflow, in which agents are not first-class.
- **[Toolhouse](https://toolhouse.ai/).** It has 40+ built-in MCP servers with agent deployment. It is ruled out because its registry semantics are minimal (no semantic search, no RBAC, no governance workflow).
- **[Docker MCP Catalog](https://www.docker.com/blog/enhancing-mcp-trust-with-the-docker-mcp-catalog/).** It is a Docker-published catalog with commit pinning, publisher trust tiers, and cosign signature verification. It is ruled out as a substrate because it is a single-vendor curated catalog, not a self-hostable registry that ABCA operators can publish to. Its supply-chain patterns (commit pinning, cosign) inform sub-decisions 3 (immutability) and 7 (descriptor validation) even though the platform itself is not adopted.
- **[Jozu Hub](https://jozu.com/mcp-registry/).** It is an MCP registry with cryptographic signing, security scanning, and runtime policy gating via Jozu Agent Guard. It is ruled out for three reasons. Its scope is narrower than that of the AWS-native option, its alignment with ABCA's Cognito and IAM auth model is unclear, and treating it as a substrate would introduce a second vendor on the critical path.
- **[Stacklok / ToolHive](https://stacklok.com/resources/building-a-local-mcp-registry/).** It is an open-source local registry with strong audit and OTEL support and vMCP for curated tool sets. It is ruled out as a substrate for the same operational reason as mcp-gateway-registry. Adopting it introduces new components (a registry service and its own auth and audit paths) without covering the governance workflow (sub-decision 10) as well as the preferred managed option does. Its audit-trail patterns inform observability decisions in the design PR.

**Design PR decision framework.** Choose the fallback (option 2) when *any* of the following is true:

- Agent Registry is not available or permitted in every target ABCA deployment region or account.
- Agent Registry's revision model cannot be constrained to enforce `(name, version)` immutability with acceptable client-side guards.
- Semver resolution added on top of Agent Registry's version string materially complicates the resolver or breaks the parity contract with WORKFLOWS.md.
- The cost of a future Agent Registry contract migration, weighed against ABCA's release timeline, exceeds the cost of building the DynamoDB and S3 fallback once.

**Deployment gate after the 2026-08-06 cutover.** ABCA now targets the standalone `agent-registry` namespace. Agent Registry is enabled by default for compatibility, but operators in an unsupported or restricted account or region deploy with `--context enableAgentRegistry=false`. That setting omits the registry, registry API, registry IAM, environment wiring, and outputs. Any remaining `registry://` reference fails closed. The migration creates a fresh registry, so operators must re-publish records or use AWS migration tooling outside ABCA. Turning the feature off on an existing stack removes the CloudFormation-managed registry and its records.

Regardless of substrate, the invariants above (semver, immutability, resolve-at-boundary, descriptor validation, governance workflow, fail-closed, resolver interface as the seam) hold.

## Consequences

- (+) **New tools, skills, and policies do not require CDK deploys.** Publishers push new versions to the registry, and blueprints re-pin when ready. The compile-and-deploy path is only for platform-level changes.
- (+) **Per-task audit.** `resolved_assets` on every task record answers "what did this task actually run" from a single field, without searching deploy timestamps or Git blame.
- (+) **Reproducibility.** A task's pins fully determine the assets it loads. Re-running the same task with the same pins produces the same asset load, apart from LLM nondeterminism.
- (+) **Registry vocabulary was pre-declared.** ADR-014 and WORKFLOWS.md anticipated the URI grammar, asset kinds, and resolver interface, so this ADR *extends* a committed shape and does not open a new one. The pre-existing `_REGISTRY_REF` check accepted a lenient `registry://kind/name` form. The implementation widens it (adding `@<constraint>` and snake_case kinds) and puts the authoritative strict grammar in `registry/ref.{ts,py}` (sub-decision 1).
- (+) **Preferred-substrate direction gives implementers a clear default.** Reviewers and future contributors don't need to argue managed Agent Registry versus first-party storage again from first principles. The trade-off is recorded with an explicit fallback rule.
- (+) **Aligned with AWS-native architecture.** AWS Agent Registry is a managed AWS service that natively covers the invariants (governance lifecycle, audit, discovery, MCP-native endpoint, IAM or JWT auth). ABCA is AWS-native by construction, so this alignment avoids re-implementing what AWS already provides.
- (+) **Governance machinery is available at MVP via the substrate.** Because ABCA chose Agent Registry, the lifecycle state model, transition APIs, CloudTrail audit, and EventBridge notifications exist from the start without ABCA building a state machine (sub-decision 10). The ABCA *interface* over that machinery is intentionally thin at MVP: publish, `auto_approve`, and read. Standalone promote, reject, and deprecate endpoints, environment-gated auto-approve, and ABCA-side event consumption are deferred to [#478](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/478) and [#230](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/230).
- (+) **Clean handoff to child issues.** [#478](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/478) (lifecycle), [#479](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/479) (versioning and immutability), [#480](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/480) (Blueprint integration and ACLs), and [#481](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/481) (capability descriptors) each map to a specific sub-decision above, so each has a scoped mandate that does not overlap the others.
- (−) **Two-language resolver contract.** The `RegistryClient` interface and the semver rules must agree between the TypeScript orchestrator and the Python agent. This is the same class of parity hazard that the repo has met twice before (Cedar bindings, workflow validation). Mitigation: publish the resolver contract as a golden corpus (`contracts/registry-resolution/`) that mirrors the existing `contracts/cedar-parity/` and `contracts/workflow-validation/` mechanisms. CI runs the annotated `(ref, catalog) → verdict` fixtures against every implementation.
- (−) **A rich descriptor schema is one more thing to maintain, and it is deferred.** A cross-kind capability descriptor (tools exposed, egress, Cedar actions, compute, permissions) would need to be authored, versioned, and evolved compatibly, with JSON Schema as the single source of truth that both languages consume (mirroring the workflow-schema decision in ADR-014). The MVP does **not** build this descriptor. It relies on the substrate's native descriptor validation (MCP `server.json`, skill frontmatter, `CUSTOM` shape checks) per sub-decision 7. The shared-schema capability descriptor lands with [#481](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/481).
- (−) **MVP access control is coarse-grained.** Two Cognito groups (`RegistryPublisher`, `RegistryApprover`) are a single tenant boundary, with no per-namespace ACL and no publisher-per-team. That is acceptable for MVP because it makes the sub-decision 10 approval workflow meaningful. Phase 3 Cedar-governed ACLs ([#480](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/480), [#481](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/481)) close the gap.
- (−) **Substrate selection required a spike.** The choice was made with evidence. A DynamoDB and S3 fallback was prototyped, and the original AgentCore-namespace implementation was built and exercised on a dev stack during review (design PRs #664 and #665). The managed Agent Registry service was selected per the flip-conditions below, and #771 later migrated it to its standalone namespace. The `RegistryClient` seam keeps the fallback available if a flip-condition is later met.
- (!) **Region and account availability.** Agent Registry may not be available or permitted everywhere ABCA is deployed. Mitigation: the default-on `enableAgentRegistry` context gate can remove the complete feature without affecting Blueprints that do not use `registry://` references. Operators must explicitly migrate or re-publish catalog data when moving from the retired preview namespace.
- (!) **Semver-on-a-non-semver-substrate.** Agent Registry's version field is a string, not a semver-aware column. The ABCA-side resolver has to (a) query candidate records and (b) rank them by parsed semver. This approach is safe when catalogs are small, but a large catalog could pay a list cost on each resolve. Mitigation: cache resolved pins per `(ref, catalog-fingerprint)` at the create-task boundary, and measure at MVP scale before optimizing.
- (!) **"Removed" and GDPR-style deletion are different.** `removed` means "fails to resolve, refuse to run tasks pinned to this". It does not necessarily mean that the bytes are gone. If a compliance-driven true deletion is ever required, it is a separate operation on the substrate and outside the resolver contract. The design PR is to note this point.
- (!) **Non-goal drift.** The MVP does not include transitive registry-asset dependencies, EventBridge as a primary bus for asset events, replacing repo-local `.mcp.json` or `AGENTS.md`, publisher-per-team ACL, or the meta-agent path from [#99](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/99). If any of these arrives through scope creep, it undermines the "resolve at task start" boundary and should be moved to a follow-up ADR.
- (!) **Federation, or a "registry of registries", is out of scope.** ABCA runs a single, **operator-curated** catalog. Trusted operators publish assets into ABCA's own registry (sub-decision 11), and assets are not federated from external indexes. External registries (the [MCP Registry](https://registry.modelcontextprotocol.io/), hubs in the style of PyPI, npm, or Docker Hub, or peer ABCA instances) are treated as **discovery sources only**. An operator may *find* an asset there and then publish it into the ABCA catalog, but the agent never resolves a `registry://` ref against an external index at task time. There is no cross-registry federation layer, and none is planned in #246. The `RegistryClient` seam (sub-decision 8) already delivers the substrate independence that federation is sometimes used for, without a second indirection. If a future need for true federation emerges, it is a new ADR, not scope creep of this one. (Review raised the question of whether to adopt a CNCF or community "registry of registries" abstraction in place of a bespoke catalog. That question is deferred with the rest of federation. The MVP's single curated catalog is deliberately the smaller design.)
- (!) **Governance for `production` publish is a trust decision.** Until Cedar-governed ACLs land, publish rights are keyed by Cognito group membership, which is a coarse gate. Any exposure of the publish endpoint outside a trusted operator group is a security decision, not a convenience decision.
