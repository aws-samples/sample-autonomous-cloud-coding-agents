# ADR-014: Workflow-driven tasks with an agent-side step runner

**Status:** accepted
**Date:** 2026-06-04
**Last-updated:** 2026-11-26
**Implementation:** Shipped ([#248](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/248)). The `task_type` enum is removed; `workflow_ref` resolves to a pinned `resolved_workflow` ({id, version}) at the create-task boundary, and the agent runs first-party workflows (`coding/new-task-v1`, `coding/pr-iteration-v1`, `coding/pr-review-v1`, plus repo-less `default/agent-v1` and `knowledge/web-research-v1`) via the agent-side step runner. The Cedar `context.read_only` migration (Phase 2a) and the repo-optional schema freeze are in place (see the 2026-06-08 addenda).

## Context

The platform supports exactly three task types: `new_task`, `pr_iteration`, and `pr_review`. They are fixed as a TypeScript union and enforced by a compile-time exhaustiveness assert. Behavior for each type is not centralized. It is spread across eight files in the Python agent runtime (`pipeline.py`, `post_hooks.py`, `repo.py`, `config.py`, `server.py`, `models.py`, `prompts/__init__.py`, `runner.py`), each of which branches on the literal `task_type` string. A Cedar policy also hard-codes `Agent::TaskAgent::"pr_review"` for read-only enforcement.

This design has two costs:

1. **Every new task type is a core-code change.** The change touches all of those files. It is high-friction, regression-prone, and gated on a CDK deploy.
2. **Non-coding tasks are impossible.** Every task clones a repo unconditionally, because `setup_repo` runs for all types. The create-task API also hard-requires an onboarded `repo` and rejects a request without one (`422 REPO_NOT_ONBOARDED`). "Requires a repo" is an implicit universal assumption. It is never a declared, switchable property.

Issue [#248](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/248) asks for **capability-driven tasks**. A declarative file describes the ordered steps to run, so coding and non-coding workflows share the same admission, memory, policy, cost, and observability machinery. Only the declarative file differs. The issue is the focused, current-architecture slice of the broader AKW vision ([#99](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/99)), and it pairs with the agent asset registry ([#246](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/246)).

Two forces constrain the design:

- **Naming collision.** "Blueprint" already names the *per-repo* CDK construct that writes `RepoConfig` (compute, model, credentials, networking). The new artifact is *per-task-type*. Overloading "Blueprint" would conflate two different scopes.
- **Existing prior art.** An unmerged branch (`origin/merge/akw-integration`, commit `9d066a8`) already ports AKW's YAML registry, the `Blueprint` and `ToolEntry` Python models, a `resolve_task()` contract, and nine example blueprints. The branch also carries LTM capability negotiation, `quality_checkpoints`, meta-agents, and Mem0, and most of that is explicitly out of scope for #248.
- **Where steps run.** The orchestrator already documents, but has not shipped, a `step_sequence` and `StepRef` model for durable, orchestrator-side custom steps (REPO_ONBOARDING.md Layers 2 and 3). The issue asks instead for steps that execute "inside the container."

## Decision

Introduce **workflows**. A workflow is a versioned, declarative YAML file that describes how the agent executes one kind of task. The file declares the ordered `steps`, the system prompt, the `agent_config`, how repo-discovered config is layered and gated, the hydration sources, the terminal outcomes, `domain`, `requires_repo`, and `read_only`. The `agent_config` covers tools, MCP servers, skills, plugins, rules or prompt fragments, and Cedar policy, and it mirrors the #246 registry asset kinds. The three shipped task types become the first three first-party workflows. The full schema and worked examples are in [docs/design/WORKFLOWS.md](../design/WORKFLOWS.md).

There are four sub-decisions:

1. **Name the artifact "Workflow," not "Capability" or "Blueprint."** The names follow scope. A Blueprint is per-repo and is unchanged. A Workflow is per-task-type and is new. A Blueprint pins which Workflows a repo may run, and a Workflow is repo-agnostic. "Capability" tested poorly for clarity. The registry in #246 still classifies workflows under its `capability` asset *kind*, with "workflow" as the ABCA-facing name. The request field is `workflow_ref`, which issue #248 calls `capability_ref`. The recorded metadata is `resolved_workflow`.

2. **Execute steps agent-side, via a new step runner.** The runner (`agent/src/workflow/runner.py`) interprets `workflow.steps` inside the container. The orchestrator's durable lifecycle (`admission-control → pre-flight → hydrate-context → start-session → await-agent-completion → finalize`) is unchanged. The workflow drives what happens within `RUNNING`, not the platform lifecycle. Existing helpers such as `setup_repo`, `run_agent`, `verify_build`, and `ensure_pr` become step handlers instead of inline branches.

3. **Reconcile-and-adopt the prior art, scoped down.** Take its proven data shapes: the per-blueprint YAML structure, the mapping of `task_mode` to `domain` plus `requires_repo`, `read_only`, the promotion `status` (`draft→validated→production→deprecated`), and the `resolve` pre-flight contract. Drop everything that overshoots #248: LTM capability negotiation and `CapabilityIndex`, Mem0, `quality_checkpoints`, meta-agents, and multi-agent loops. The resolver interface is designed so that #246's registry backend is a drop-in replacement for the filesystem backend.

4. **Remove `task_type` and resolve `workflow_ref` at the create-task boundary.** This work replaces the `task_type` enum. The enum is deleted, not preserved as an alias, because carrying both would defeat centralizing per-task-type behavior. `workflow_ref` becomes the sole task-selection field. It is resolved (`ref + constraint → pinned {id, version}`) where `task_type` is validated today, in `create-task-core.ts`. When `workflow_ref` is absent, resolution falls back to the Blueprint default and then to the platform `default/agent-v1`, so there is always a workflow. The removal is an intentional breaking API change, acceptable pre-1.0. Existing `task_type` callers migrate through a published one-to-one map, for example `new_task → coding/new-task-v1`. Functional fidelity of the migrated coding paths is a goal that the promotion gate (tests and eval) verifies. It is not a hard byte-for-byte constraint. Intentional behavior changes are recorded in the migration PR.

### Why agent-side over orchestrator-side steps

The orchestrator-side `StepRef` and `step_sequence` model is real but unshipped. Moving per-step workflow logic into durable Lambda steps would have three costs. It would be a far larger change to the durable execution path. It would overlap the separate planned work on "Blueprint custom steps". It would contradict the issue's "inside the container" framing. Agent-side execution keeps the change out of durable orchestration. The platform's invariants (concurrency, audit, cancellation, timeouts) are untouched. The workflow reshapes only the agent's own execution, the unpredictable part that the architecture already isolates in the compute session.

## Consequences

- (+) **New task types are authored, not coded.** A new coding or knowledge workflow is a YAML file plus registered step handlers. It needs no edits across eight runtime files and a Cedar policy, and no CDK deploy.
- (+) **Repo-optional tasks unlocked.** `requires_repo:false` skips repo onboarding enforcement, GitHub pre-flight, clone, and PR finalization. Knowledge work can then run from `task_description` and attachments alone.
- (+) **Always a workflow.** With `task_type` gone, resolution tries `workflow_ref`, then the Blueprint default, then the platform `default/agent-v1`. A submission with no `workflow_ref` therefore gets a minimal "run the request through the agent" default and is not coerced into the heavyweight `new_task` path.
- (+) **Per-task-type model preference, safely bounded.** `agent_config.model` lets a workflow prefer a Bedrock model. The model is validated against the platform and Blueprint allow-list, and an unpermitted model fails admission. The per-task budget still caps the cost. A workflow can choose a model without escalating privilege or cost.
- (+) **Provider-neutral repo vocabulary.** `repo_config.provider` and a `VcsProvider` seam name the GitHub-specific operations (PR, review, and permission) as instances of the generic "change proposal" and "review" concepts. Adding GitLab, Bitbucket, or another provider later is therefore not a schema or contract break. `github` is the only implemented backend in #248.
- (+) **Single source of truth per task type.** The scattered `task_type` branches (`PR_TASK_TYPES`, `_PROMPTS`, `is_read_only`, the Cedar `pr_review` string-match) become declared workflow fields. Both `allowed_tools` and Cedar enforce read-only. Today only Cedar enforces it, and the change closes that gap.
- (+) **Audit and eval.** `resolved_workflow` is pinned on every task. The existing progress writer emits per-step milestones. Cost is segmented by `domain`.
- (+) **Promotion is earned, not asserted.** A declared `promotion_gate`, a behavioral eval per workflow, gates `status: production`. The gate is layered onto the ADR-013 validation pyramid, so quality is machine-checked at the transition and not claimed in a PR description. The gate verifies that a workflow does the right thing. It therefore permits intentional behavior changes, recorded alongside the eval update, and does not enforce byte-for-byte parity with today.
- (+) **Discovery separated from execution.** The optional `description` and `guidance` fields give people and agents text to select a workflow by, in registry search and in `bgagent workflow list`. That text is distinct from the machine-facing `prompt`.
- (+) **Clean path to the registry (#246).** Workflows are filesystem-backed first and registry-resolved later, with a stable `resolve` contract. The asset kinds of `agent_config` (tools, mcp_servers, skills, plugins, subagents, prompt_fragments, cedar_policy_modules) mirror the #246 vocabulary one to one, so a workflow is the registry's first concrete consumer.
- (+) **Full agent config in three planes.** A workflow declares the whole SDK session shape, not only the tools. The config is layered as Blueprint (per-repo) < `agent_config` (per-task-type) < repo-discovered `.claude/` and `.mcp.json`. A workflow can gate the repo plane through `repo_config`. Skills, plugins, subagents, and prompt_fragments are forward-declared but registry-resolved (Phase 4), so the schema is complete without implying Phase-1 behavior.
- (−) **Two related but distinct concepts.** Blueprint and Workflow together give the platform more concepts to learn. The strict framing of per-repo against per-task-type and the naming note in WORKFLOWS.md mitigate the cost.
- (−) **A new schema and validator to maintain.** The schema is JSON Schema, and the validator is a synth-time and CI lint over `agent/workflows/**`. The `workflow_ref` and `resolved_workflow` fields also now span the type-sync contract between CDK and CLI. Three measures avoid re-creating the cedar-parity drift hazard. First, the JSON Schema is the single canonical shape contract. Both the TS synth validator and the Python loader consume it through standard libraries and do not re-implement it. Second, the non-schema cross-field rules have exactly one implementation in Phases 1 to 3. That implementation runs at CI time. The runtime loader does shape-only validation and trusts the CI verdict. Third, a `contracts/workflow-validation/` golden corpus locks any Phase-4 second implementation to parity. The corpus holds annotated expected verdicts and runs against every validator implementation, the same mechanism as `contracts/cedar-parity/`. See WORKFLOWS.md §"Single source of truth and validator parity".
- (−) **Breaking API change.** Removing `task_type` breaks existing callers. They must move to `workflow_ref` through the published map. The break is acceptable pre-1.0, but it is a hard cutover with no dual-field grace period. The migration map and the CLI rework must therefore ship together and be documented in API_CONTRACT.md.
- (!) **Migration risk.** Moving the three shipped paths onto the runner can change behavior. The main mitigation is to substitute the runner for the branches without rewriting helper logic. The existing handler and agent tests and the #236 E2E gate the move. Where behavior changes intentionally, the migration PR calls out the change, so it does not pass unnoticed.
- (!) **Memory keying.** Long-term memory is keyed on `repo`. Repo-less workflows need a fallback actorId. The fallback is an open question in WORKFLOWS.md, to coordinate with MEMORY.md.
- (!) **Single `run_agent` invariant.** The runner enforces exactly one agentic step for now. Lifting that limit, for multi-agent workflows, is deliberately deferred to #99.
- (!) **Cedar principal migration is security-critical.** Read-only enforcement moves from a literal `"pr_review"` match to a rule driven by `context.read_only`, so that it applies to all read-only workflows. The move must be done precisely, and the existing Cedar parity fixtures gate it. An error here *silently weakens* enforcement, because the rule stops matching, and does not fail loudly. Reviewers of the policy rewrite and the regenerated parity fixtures must therefore keep that property in mind. The schema enforces a policy floor, in which soft-deny is mandatory for writeable workflows, so a workflow file cannot weaken the HITL posture by config. **(Superseded. See Addendum 2026-06-08 on Phase 2a sequencing.)**
- (!) **Resume-aware steps, not orchestrator-durable steps.** The runner checkpoints step completion to persistent session storage (`/mnt/workspace`, which survives stop and resume). It resumes the agent loop through the persisted SDK session UUID. A stop and resume therefore skips completed steps and does not replay from turn 0. This recovery is agent-side. The orchestrator still treats the session as one `await-agent-completion` step, so the invariants stay outside the agent. Worker-portable resume depends on the planned S3-backed SDK session store, tracked as a GitHub issue. Until that store ships, a total worker loss falls back to a re-run from step 0, and mandatory step idempotency mitigates the re-run. `on_failure: continue` after side effects is forbidden. Per-step compensation or rollback is a non-goal.
- (!) **Promotion gate bootstrapping.** A behavioral eval per workflow depends on #236. Until #236 lands, the gate is a concrete test target and, when omitted, a reviewed manual step. "Earned, not set" arrives in stages and is weakest for the phases that ship first.
- (!) **Repo-optionality is a wider refactor than Phase 3's one-liner implies.** `repo` is required across about 6 TS interfaces and the agent config validator. Memory keying, SessionRole tenant tags, and artifact delivery all assume a repo. The `requires_repo:false` promise in the Phase-0 schema is a forward-declaration, not a runnable path. The `web_research` example is a schema-expressiveness fixture, not yet an executable acceptance test. The two blocking open questions (memory actorId and the artifact delivery contract) must be resolved as recorded decisions, in a short ADR addendum, before the Phase-0 schema is frozen. Either question may add or reshape a schema field, for example `actor_namespace` or the `deliver_artifact` target contract. Deferring them past the freeze risks a breaking schema revision.
- (!) **Governance.** Publishing or promoting a `production` workflow is a trust decision and follows ADR-003. Registry-era publish ACLs are Cedar-governed per #246 Phase 3.

## Addendum (2026-06-08): Phase 2a sequencing — isolated PR requirement dropped

The original decision required the Cedar principal migration (Phase 2a) to ship as its own isolated PR, reviewed alone and landing ahead of the `pr_iteration` and `pr_review` workflow migrations (Phase 2b). That ordering is no longer achievable on the as-built branch. The cutover from `task_type` to workflows (Phase 2b) already shipped without the Cedar change. A deliberate bridge made the cutover safe. `policy_principal_for()` maps `read_only ⇒ "pr_review"`, so the existing literal-principal `forbid` rules in `hard_deny.cedar` keep firing for every read-only workflow. Read-only enforcement is therefore already correct under the legacy principal. Phase 2a is a refactor of how that enforcement is keyed, from `principal == Agent::TaskAgent::"pr_review"` to `context.read_only == true`. It does not close a gap.

With the bridge in place, the "isolated PR ahead of 2b" rule has lost its purpose, because there is no window where 2b runs without protection. We therefore drop the isolation and ordering requirement and implement Phase 2a as commits on the existing `feat/248-workflow-driven-tasks` branch. Other means preserve the security property that the rule protected, and those means remain mandatory:

1. The `contracts/cedar-parity/` golden fixtures gate the migration. They run against both the Python `cedarpy` and the TypeScript `cedar-wasm` bindings (decision #23). The fixtures are updated in the same commit as the policy rewrite.
2. A dedicated parity fixture for the `context.read_only` deny path is added, so a golden vector locks the matching behavior of the new rule. A regression in which the rule silently stops matching then fails CI and does not ship.
3. The bridge in `policy_principal_for()` is removed only after the `context.read_only` rule is in place and fixture-verified, in the same change. There is never a window where neither keys the deny.

Two things do not change. Both `allowed_tools` (no Write or Edit) and Cedar still enforce read-only. The schema's soft-deny policy floor for writeable workflows stands. Reviewers should still treat the `hard_deny.cedar` and `policy.py` context diff as the security-critical core of this PR, and review it with the "silently weakens" failure mode in mind.

## Addendum (2026-06-08): repo-optional open questions resolved — schema freeze

[WORKFLOWS.md](../design/WORKFLOWS.md) open questions #1 (memory actorId for repo-less tasks) and #2 (artifact-delivery contract) were flagged as blocking Phase 3 and requiring resolution before the Phase-0 schema is frozen, because either might add or reshape a schema field. Both are now decided. The schema field reshape implied by #2 is applied in the same change as this addendum, so the schema can be treated as frozen.

**Decision 1. Memory actorId for repo-less tasks is per-user (`user:{id}`).** A repo-less task uses `actorId = user:{cognito_sub}`, not the `repo` that coding tasks use (`memory.py`). The Cognito subject is the platform user id already threaded as `TaskConfig.user_id`. The rationale has two parts. The key is caller-scoped, so no knowledge bleeds across tenants, the same isolation property that the per-user trace prefix already relies on. The key also matches the platform's existing user-scoping pattern. Cross-*workflow* knowledge pooling (for example, "all `web_research` tasks share learnings") is explicitly not adopted now. Pooling mixes tenants in one namespace and is a larger privacy decision that can be deferred to the registry phase.
  - **Schema impact: none.** The key is a fixed platform fallback and is not author-configurable, so it adds no `actor_namespace` selector to the workflow schema. The earlier note that it "may introduce an `actor_namespace` selector" is resolved in the negative, and the schema stays smaller. The decision is a Phase-3 `memory.py` change. When `repo` is absent, `memory.py` keys on `user:{user_id}`. Coding tasks are unchanged.

**Decision 2. Artifact delivery uses named Python deliverers (open `target`), with the shared S3 plumbing pinned now.** `deliver_artifact.target` becomes an open string that resolves to a registered Python deliverer. The step-handler registry (`STEP_HANDLERS` in `runner.py`) follows the same "author, don't code the core" pattern. A new delivery method is a new registered deliverer function, not a schema change. The open string keeps the field forward-compatible with #246, where a registry-resolved deliverer is a drop-in for the filesystem one. The field does not pin a closed `s3 | comment | s3_and_comment` enum that every new method would have to widen.
  - **Plumbing pinned now.** All deliverers share the plumbing, so it can freeze. Artifacts upload to a task-scoped S3 key, `artifacts/{task_id}/<name>`, in a platform artifacts bucket. The agent SessionRole gets an IAM grant scoped to that prefix, mirroring the `traces/{user_id}/` per-prefix guard. A size limit applies per artifact. The URL of the delivered artifact appears on `TaskDetail`. The SessionRole `repo` tenant tag gains a repo-less form, a `workflow:{id}` tag, so the role is still attributable without a repo.
  - **Deliverer contract.** Each registered deliverer declares the set of terminal outcomes it `produces`. For example, an S3 deliverer produces `artifact`, and a comment deliverer produces `comment`. Validator rule 11 is today a hardcoded `target → outcomes` map, `_DELIVER_TARGET_OUTCOMES`. The rule is reframed to consult the deliverer registry instead of the enum, so the "declared `primary` outcome is actually produced by some step" check survives the move to open targets. Until Phase 3 ships real deliverers, the registry carries the three first-party names (`s3`, `comment`, `s3_and_comment`) with their existing produced-outcome sets. No current workflow, fixture, or `contracts/workflow-validation/` golden vector therefore changes behavior. The enum is widened to an open string plus a registry, not redefined.
  - **Schema impact, applied with this addendum.** `steps[].target` drops its `enum` constraint and stays `type: string`. The closed set moves into the deliverer registry. `deliver_artifact` itself remains a `NotImplementedError` stub until Phase 3. Only the contract is frozen here, not the implementation.

With both questions resolved and the one schema reshape applied, the Phase-0 schema is frozen. Subsequent phases add registered handlers, deliverers, and platform plumbing, not schema fields.
