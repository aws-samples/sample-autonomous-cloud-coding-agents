> **2026-07-21 revision.** The outbound design was restructured to separate **execution semantics** (deterministic REST or GraphQL from Lambda) from **credential transport** (the AgentCore Identity vault). See *Linear is fully deterministic* below.

> **2026-08-28 implementation note. Phase 1 (Linear `ChannelCredential`) is built and live-verified on a dev stack** ([#809](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/809)). The change is additive and context-gated (`enableLinearIdentityVault`, default off), and Secrets Manager is retained as the fallback, so a deployment that does not opt in is byte-for-byte unchanged. The decision below stands. Two implementation details deviate from the P1 text and are recorded in *Phasing*, under P1.

## Context

ABCA propagates *who* as data but not as an enforceable credential. Issue [#245](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/245) threads the user identity through traces and logs (`cognito+<sub>`), so attribution is correct. The same identity does not yet gate a token. Two costs follow from that gap:

1. **Inbound identity is hardwired.** CLI and REST callers authenticate to an Amazon Cognito User Pool. Webhooks (GitHub, Linear, now Jira) authenticate with HMAC-SHA256 shared secrets in Secrets Manager. Both verification paths are hard-coded in handler code. An operator who runs their own Okta, Microsoft Entra, or Keycloak cannot swap the inbound provider without editing handlers.

2. **Outbound auth is N hand-rolled resolvers.** Each integration re-implements credential fetch, refresh, and refresh-race handling against Secrets Manager.

   - `resolve_github_token()` (`agent/src/config.py`): one shared PAT for all repos and users. No per-user or per-repo scoping.
   - `resolve_linear_api_token()` (`agent/src/config.py`) and `cdk/src/handlers/shared/linear-oauth-resolver.ts`: per-workspace OAuth token. The Lambda resolver refreshes it manually inside 60s of expiry, with one-shot rotation-race handling, and writes the new tokens back to the secret. The agent resolver does not refresh, because the agent's role holds `GetSecretValue` only and could not store the refresh token that Linear rotates on every use. It reads the stored token and returns no token when the stored one is inside 60s of expiry.
   - The Jira resolver added in PR [#302](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/pull/302) and extended by issue [#642](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/642): one per-tenant Secrets Manager bundle holds 3LO for reads and human lookup, plus the signed Forge app-actor proxy for writes.

   A second provider that arrives through the same `resolve_<integration>_token()` shape is live evidence that the seam already exists. The seam is not yet named or unified.

**The AgentCore path already exists but is dormant.** ABCA runs on AgentCore Runtime, and the Workload Access Token (WAT) propagation path is already wired:

- The orchestrator sets `runtimeUserId` on `InvokeAgentRuntimeCommand` (`agentcore-strategy.ts:58`).
- The dispatcher holds `InvokeAgentRuntimeForUser` (`task-orchestrator.ts:429-430`).
- The agent reads the `WorkloadAccessToken` header and re-injects it across the pipeline thread (`server.py:214-220, 301-314`).

`bedrock-agentcore` stays in `agent/pyproject.toml` as a vestigial dependency. The Phase-2.0a AgentCore Identity attempt was parked on a USER_FEDERATION service-side bug, so Phase-2.0b reads Secrets Manager directly. The platform side has since moved. AgentCore Identity became generally available on 2025-10-13, and the OBO (`ON_BEHALF_OF_TOKEN_EXCHANGE`) flow became generally available in April 2026 across 14 regions. This ADR records the decision to resume that path instead of building a credential plane from scratch. The RFC behind the decision is issue [#249](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/249).

> **Phase 0 re-validation, executed 2026-06-14 (`us-east-1`): GO-LIKELY.** A throwaway spike confirmed that the parked USER_FEDERATION bug does not reproduce in the current service build. The PAR (`request_uri`, RFC 9126) parameter that was the prime no-go suspect stays on AgentCore's own front-channel. AgentCore then redirects to the downstream provider with plain authorization code plus PKCE, so no `request_uri` reaches the provider. The production-shape JWT binding (`get_workload_access_token_for_jwt` on the IdP's `(iss, sub)`) and the substrate-independent path (vault calls from a non-Runtime boto3 context) both passed. The one step left for a full GO is a human OAuth-consent click, which cannot run headless. The recorded result is on [#249](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/249). That result is what reopens Phase 1.

## Decision

Introduce a **pluggable identity-and-auth abstraction with two seams**: one for inbound principal verification and one for outbound credential resolution. The verification provider and the token backend each become swappable behind a contract. AgentCore Identity is one implementation, not the only path.

There are four sub-decisions, one inbound and three outbound. The three outbound sub-decisions (execution semantics, deterministic-credential source, and the MCP control plane) are kept deliberately separate:

1. **Inbound: an OIDC-descriptor seam.** Abstract "who is the inbound principal and how is it verified" into a descriptor, so that Cognito can be swapped for Okta, Microsoft Entra, Keycloak, or any OIDC provider without handler changes. The descriptor maps to a CUSTOM_JWT-style authorizer shape: a `discoveryUrl` (which must end `/.well-known/openid-configuration`) plus `allowedAudience`, `allowedClients`, and `customClaims` gates that must all pass. AgentCore Runtime's `customJWTAuthorizer` is **one** implementation behind the seam. ABCA's own Cognito authorizer plus the SigV4 user-header path (`X-Amzn-Bedrock-AgentCore-Runtime-User-Id`) is another. The adapters are Cognito (shipped), Okta, Entra, and Keycloak.

   | Adapter | Discovery | Notes |
   |---|---|---|
   | Cognito | User Pool `/.well-known/openid-configuration` | Shipped today. The SigV4 path carries the user id as a header. |
   | Okta | Org or custom-auth-server discovery URL | Standard OIDC. `allowedClients` gates the app. |
   | Entra | v2 tenant discovery URL | Issue **plain** JWTs. Entra emits *encrypted* access tokens when an app registration has confidential optional claims, and the JWT authorizer cannot decrypt them (it fails silently). Use v2 with a custom exposed-API scope, or v1 with `<application-id>/.default`. |
   | Keycloak | Realm discovery URL | Private-IdP reachable via a private endpoint where the realm is not internet-facing. |

2. **Separate execution semantics from credential transport.** Two questions that earlier drafts conflated must stay separate. The first is *how an operation executes*: as a deterministic REST or GraphQL call that the platform must make reliably, or as an LLM-driven MCP tool call. The second is *where its credential comes from*, which is the vault. The operation's reliability requirement fixes the execution semantics. The credential backend does not.

   - **Deterministic Linear operations remain direct GraphQL calls from Lambda.** All the exactly-once, idempotent, structural operations stay as direct `api.linear.app/graphql` calls in the Lambda tier. These operations are the iteration threaded reply and epic status block, reactions (👀→✅/❌), state transitions, and the sub-issue DAG. **We do NOT move these into MCP and we do NOT build a custom Linear MCP facade.** MCP is best-effort and LLM-driven, so the platform UX cannot depend on it. Only the *credential source* under these calls changes, from Secrets Manager (SM) to the vault. The call sites, GraphQL documents, and Lambda ownership do not change.

3. **Lambda credentials come from AgentCore Identity, through one shared channel workload identity, keyed per workspace.** The deterministic Lambda calls above resolve their token from the vault, not Secrets Manager.

   - **One shared workload identity, `abca-linear-channel`, serves all Lambda consumers.** The **six Lambda IAM roles do NOT each need their own workload identity**. They are distinct IAM principals that are all granted access to the same credential domain. This corrects an earlier draft. Per-role workload identities were never required.
   - **The credential is keyed by `linear-workspace:<workspace_id>`.** It is a workspace-scoped platform credential, not a per-user one. The key is the `user_id` component of the vault's `(workload_identity, user_id)` key, repurposed as a workspace subject. The triggering **user identity is retained only for audit attribution** (#245's `cognito+<sub>` in traces and logs), **not** for credential selection on the deterministic path.
   - **Multiple Lambda IAM roles may read that one credential domain.** IAM `Resource` scoping on `GetResourceOauth2Token` grants each of the six roles access to the `abca-linear-channel` workload identity and the Linear credential provider. The roles resolve the *same* workspace-keyed credential, and there is no per-role consent. **Correction to an earlier draft.** The mechanism is *N IAM roles → 1 workload identity → 1 vault entry* (per `(abca-linear-channel, linear-workspace:<id>)`). It is **not** "multiple *workload identities* share one vault entry." Distinct workload identities key distinct vault entries. Sharing comes from many IAM principals that present the *same* workload identity, not from vault sharing across workload identities.
   - **Secrets Manager refresh and write-back retire eventually.** Once the vault owns the token and its refresh, the `PutSecretValue` grants on the five Lambda roles and the `tryRefreshOnce` write-back in `linear-oauth-resolver.ts` are removed. The retirement is phased, not a single cutover. The SM fallback stays until the vault path is green.

   This credential is the **`ChannelCredential`** type (see *Credential types* below), a platform or workspace credential for deterministic vendor APIs. Linear's `ChannelCredential` keeps ABCA's existing `actor=app` OAuth application. The Lambda GraphQL calls already use that app-actor token, and it belongs on the deterministic path.

   **Deterministic consumer inventory (verified 2026-07-21, file:line-exact).** These consumers are what migrates to the `ChannelCredential`:

   | Plane | Where | Uses | Linear operations (all direct GraphQL) |
   |---|---|---|---|
   | **Lambda tier** | `cdk/src/handlers/**`. 6 deployed functions (WebhookProcessor, Orchestrator, Reconciler, FanOut, Sweep, GitHub-screenshot), each with its own IAM role. 7 direct `resolveLinearOauthToken` sites and a `resolveToken()` wrapper that fans out to 13 feedback functions | `abca-linear-channel` workload identity (WI), keyed `linear-workspace:<id>`. 5 of 6 hold `PutSecretValue` **today** (retires) | Iteration UX and orchestration: `CreateComment`/`UpdateComment`/`DeleteComment`/`ReplyToComment`/`upsertThreadedReply`, `ReactIssue`/`ReactComment`/`UnreactIssue`/swaps, `SetIssueState`/revert (`linear-feedback.ts`). `SubIssueGraph`/`IssueParent` (`linear-subissue-fetch.ts`). `IssueByIdentifier` (`linear-issue-lookup.ts`). `IssueContext`. `IssueText` |
   | **Agent container** | `agent/src/**` | Runtime WI. WAT injected by the Runtime SLR | Reactions and forward-only status transitions (`linear_reactions.py`). Same `ChannelCredential` domain, resolved via the Runtime `WorkloadAccessToken` header |

   The same shape holds for **Jira** (`jira-oauth-resolver.ts`, 5 Lambda sites plus `jira-feedback.ts`, and the agent's `jira_reactions.py`). A Lambda-only shape holds for **Slack** (`slack-notify.ts`, no agent token). The `ChannelCredential` domain is per-`(surface, workspace)`. The workload identity is shared per surface (`abca-<surface>-channel`).

4. **MCP is a separate, first-class control plane, and every registered MCP executes through AgentCore Gateway.** MCP tool-use is not a per-surface transport toggle. It is its own registration and execution plane, independent of the deterministic credential above.

   - **Users or workspaces register MCP servers and bind their tools to agents or workflows.** Registration is explicit and first-class, not derived from vendor capability flags.
   - **Every registered MCP executes through AgentCore Gateway. There is NO direct-MCP fallback.** The agent never writes a `.mcp.json` that points straight at a vendor MCP. If the Gateway cannot front a registered MCP, that MCP is unavailable.
   - **Unsupported authentication fails closed.** If the Gateway cannot obtain a working credential for a registered MCP (for example, because the vendor's OAuth cannot satisfy the Gateway's flow), that MCP does not load. It is not silently routed direct and is not degraded to a weaker mode.

   The **`McpRegistration`** and **`McpCredential`** types describe this plane (see *Credential types* below).

   > **Rejected: the capability-flag transport model.** An earlier draft derived a per-surface transport (`Identity-direct`, `Gateway-fronted`, or `Hybrid`) from two coarse flags (`lifecycleViaGateway`, `gatewayOAuthOk`). That framing is **rejected** for three reasons. It conflated execution semantics with credential transport. It treated MCP as a fallback, not a control plane. It is not a sufficient abstraction, because two boolean flags cannot capture per-tool bindings, per-user grants, or fail-closed auth. Deterministic operations are always direct GraphQL from Lambda (§2). MCP is always Gateway (§4). There is no "hybrid transport" toggle.

### Why a seam, not a rewrite

The abstraction is intentionally a contract, not a wholesale move of credential handling onto AgentCore:

- **Backend-agnostic.** One `resolve_<integration>_token()` contract serves both the AgentCore Runtime backend (where the token arrives in the `WorkloadAccessToken` header) and the parked ECS backend (in-process boto3). The backend decides how the token arrives. The seam is the same for both.
- **Incremental.** The rollout is phased and flag-gated, and the shared PAT fallback stays until the vault path is green. There is no single cutover.
- **Consistent with ADR-014.** This abstraction is the credential-plane analog of the provider-neutral `VcsProvider` seam in [ADR-014](/sample-autonomous-cloud-coding-agents/decisions/adr-014-workflow-driven-tasks). The `VcsProvider` seam named GitHub-specific control-plane operations as instances of generic concepts. This one names the per-integration credential resolvers as instances of one outbound contract.

## Credential types

There are three distinct types, deliberately not collapsed into one "token":

- **`ChannelCredential`.** A **platform or workspace** credential for the **deterministic** vendor APIs (§2, §3). The subject is `linear-workspace:<workspace_id>` (workspace-scoped, not per-user). AgentCore Identity backs it under the `abca-<surface>-channel` shared workload identity. The Lambda tier and the agent's `linear_reactions.py` use it for direct GraphQL. For Linear it wraps ABCA's existing `actor=app` OAuth application.
- **`McpCredential`.** A **user or workspace** grant for **Gateway tools** (§4). The Gateway presents this credential outbound to a registered MCP server. The preferred subject is per-user, so that tool-use is attributable to the triggering user. A workspace-scoped subject is a fallback where per-user is not meaningful. Linear does not use this type, because Linear has no MCP leg (see *Linear is fully deterministic* below).
- **`McpRegistration`.** The registration record for a Gateway-fronted MCP: `endpoint`, exposed `tools`, `scopes`, the credential `subject` (which `McpCredential` binds), and the `agent` and `workflow` bindings that say which agents may use which tools.

`ChannelCredential` and `McpCredential` are **separate credentials even for the same vendor**. They have different subjects (workspace versus user), different consumers (Lambda GraphQL versus Gateway), and different lifecycles. They are not two views of one token.

## Linear is fully deterministic — no Linear MCP (decided 2026-07-21)

The Gateway remains ABCA's general MCP control plane (§4) for any MCP server that a user or workspace registers. **Linear specifically is removed from the MCP path entirely** and is handled **100% deterministically** on the one `@bgagent` `ChannelCredential`.

**Why (live-validated 2026-07-21).** Linear MCP through the Gateway does not work on one OAuth app. A fresh `actor=user` Gateway target reached `READY`, but **every data read failed** with "An internal error occurred" (`get_issue`, `list_issues`, and `list_documents`, retried). An `actor=app` Gateway target **cannot consent at all**, because Linear's "already installed" response ends the authorization-code flow for an installed app. A second Linear app is rejected because of identity fragmentation. The agent must present one Linear identity, `@bgagent`. There is therefore no viable path for Linear MCP via Gateway. Instead of carrying an optional but broken leg, **retire Linear MCP.**

**What replaces the 9 `mcp__linear-server__*` tools.** Nothing is lost. Each tool has a deterministic replacement:

| Removed MCP tool | Deterministic replacement |
|---|---|
| `save_comment`, `save_issue`, `list_issue_statuses` | Already deterministic in the Lambda tier (`linear-feedback.ts`: comment create and update, `SetIssueState`, `IssueTeamStates`). The agent's MCP writes were redundant and best-effort, so they are dropped. Lambda owns writes. |
| `get_issue`, `list_comments`, `list_documents` | Pre-hydrated at task creation. Extend #176 `context-hydration.ts` with Linear issue text and comments. Lambda already fetches `IssueText` and `IssueContext`. The agent receives the context in the payload, with no live MCP. |
| `get_attachment`, `extract_images`, `get_document` | Authenticated fetch on the `ChannelCredential` path. Extend #176 `resolve-url-attachments.ts` to attach the `@bgagent` bearer for `uploads.linear.app` URLs, which #176 skips today because its resolver is unauthenticated. One app, one identity, screened like every other attachment. |

**Consequences of removing Linear MCP.** Remove `_build_linear_entry` and `_linear_server_entry`, and the `"linear"` entry in `CHANNEL_MCP_BUILDERS` (`agent/src/channel_mcp.py`). Strip the `mcp__linear-server__*` guidance from `prompt_builder.py`. The agent no longer needs any Linear token for MCP. The per-thread `LINEAR_API_TOKEN` for MCP retires, and the direct GraphQL in `linear_reactions.py` keeps its own `ChannelCredential`. The Gateway substrate (`bgagent-linear-gw-*`, the M2M inbound, `gateway_auth.py`) is **not** wired for Linear. It stays available for the general MCP control plane.

**Rejected (corrections to earlier drafts):**
- **No Linear MCP at all.** This supersedes the earlier "optional Linear MCP via `actor=user` Gateway grant". That path is live-proven non-functional on one app.
- **No two Linear OAuth apps.** One app, `@bgagent`, deterministic.
- **No claim that two `actor=app` authorization-code prompts can coexist.** Linear's docs are explicit that non-`client_credentials` app tokens cannot exist in parallel. The point is moot now that Linear has no MCP leg that needs a second grant.
- **The general MCP Gateway control plane (§4) stands.** This decision is Linear-specific. It is not a retreat from Gateway-fronted MCP for other registered servers.

## Identity propagation for per-user MCP is UNRESOLVED

Per-user `McpCredential` selection requires the Gateway to know *which task-user* is invoking. That problem is not yet solved:

- **Today the Gateway inbound auth uses an M2M JWT** (a Cognito client-credentials token that the agent mints). An M2M token identifies the *workload*, not a user.
- **An M2M inbound JWT cannot select a per-user vaulted MCP credential.** The JWT has no task-user subject for the vault to key on, so per-user MCP is not achievable on the current inbound path.
- **Before claiming per-user MCP support, this ADR requires a specified, trusted task-user identity propagation.** The identity must propagate from the triggering event to the agent and then to the Gateway inbound, for example as a user-scoped JWT or as a verified user-id claim that the Gateway authorizer trusts. Until that propagation is designed and validated, `McpCredential` is workspace-scoped at best, and per-user MCP tool attribution is not possible. This is an explicit open item, not an assumed capability.

## Consequences

- (+) **One credential abstraction, not N resolvers.** New integrations register an adapter against one contract instead of re-implementing fetch, refresh, and race handling per provider.
- (+) **Execution semantics and credential transport are separate axes.** Deterministic operations are always direct GraphQL from Lambda. MCP is always Gateway. There is no per-vendor "transport mode" to special-case, because an operation's reliability requirement fixes the split, not the vendor. This supersedes the rejected two-flag derivation (`lifecycleViaGateway` and `gatewayOAuthOk`).
- (+) **Three explicit credential types, not one token.** `ChannelCredential` (workspace-scoped, deterministic APIs), `McpCredential` (user-scoped, Gateway tools), and `McpRegistration` (endpoint plus tool and workflow bindings) let the deterministic plane and the MCP plane be reasoned about independently and fail closed independently.
- (+) **Workspace-scoped `ChannelCredential` replaces the shared PAT or per-workspace SM secret with a vault-managed credential.** Deterministic APIs bind to `linear-workspace:<id>` (not per-user). The vault owns refresh, so the SM refresh and write-back retire. Per-**user** scoping applies to `McpCredential` only. It is gated on identity propagation (below) and is not assumed.
- (+) **Cryptographic attribution is available on the MCP and OBO path where per-user identity reaches the Gateway.** OBO delegation carries an `act` claim (`user ← agent`) that can be joined to #245's `trace_id` and #237's `correlation`. NOTE: on the deterministic `ChannelCredential` path the acting identity is the workspace app-actor, so per-user *credential* attribution there comes from #245 logs, not the token. Cryptographic per-user attribution requires the unresolved task-user propagation (P5).
- (+) **Operators can bring their own IdP.** The inbound descriptor lets a deployment run on Okta, Entra, or Keycloak without forking handler code.
- (+) **Backend-agnostic.** The same seam serves the AgentCore Runtime and ECS backends, matching the design posture already documented for the SessionRole in [SECURITY.md](/sample-autonomous-cloud-coding-agents/architecture/security).
- (−) **A new abstraction plus an adapter registry to maintain.** Two seams and their adapter sets add to what the platform maintains. The cost is mitigated by keeping the inbound descriptor a parameterization of a single verification path (see the risk below) and the outbound contract a thin selector over the existing flows.
- (−) **AgentCore Identity adds a managed dependency and token-vault cost.** Vault fetches (`GetResourceOauth2Token` and `GetResourceApiKey`) bill at `$0.010/1,000`. The ECS in-process resolver path remains available where that dependency is unwanted.
- (!) **Per-user MCP is not yet achievable, because task-user identity propagation is unresolved.** The Gateway inbound is an M2M JWT that identifies the workload, not the user, so it cannot select a per-user `McpCredential`. The propagation must be designed and validated (P5) before per-user MCP is claimed. Until then MCP credentials are workspace-scoped at best.
- (−) **Linear loses MCP tool-use, and deterministic paths replace it.** The 9 `mcp__linear-server__*` tools retire. Writes were already deterministic in Lambda. Reads become pre-hydrated context (#176 `context-hydration.ts`) plus authenticated attachment fetch (#176 `resolve-url-attachments.ts` with the `@bgagent` bearer). The cost is that the agent can no longer make *arbitrary* live Linear queries mid-task. It works from pre-hydrated context. The cost is accepted, because Linear MCP via Gateway is live-proven not to work on one app, and a second app is rejected. The general MCP Gateway control plane (§4) is unaffected, because this decision is Linear-specific.
- (!) **The inbound seam must not become a second auth code path.** A descriptor that grew its own verification logic would drift from the shipped Cognito and HMAC path and create two implementations to keep in sync. That is the cedar-parity drift hazard that ADR-014 calls out. The mitigation is exactly **one** inbound verification implementation. The descriptor only parameterizes it (discovery URL, audience, client list, claim gates) and never reimplements it.

**Substrate update, `lambda-microvm` (#852).** The optional split network provides headroom for MicroVM plus the vault, including additive deployments that retain AgentCore. Explicit `compute_types=lambda-microvm` also permits a MicroVM-only deployment. The production 490-resource guard validates the complete configuration. The guest execution role has the mint grant. The shared `platform_config` contract now forwards vault enablement and workload identity. A rebuilt compatible MicroVM image and a live consent and mint rehearsal are required before using the combination. Lambda MicroVMs remains experimental.

**Substrate independence (verified 2026-07-21, both proven live).** The vault path works on any compute. AgentCore Runtime injects the Workload Access Token as the `WorkloadAccessToken` header. ECS, Fargate, and Lambda bootstrap the token through `GetWorkloadAccessTokenForJWT(workloadName, userToken=<Cognito M2M JWT>)` against a **standalone** (non-service-linked) workload identity, then call `GetResourceOauth2Token`. Runtime-managed (service-linked) workload identities cannot self-vend, so the ECS path needs a manually created workload identity. The runtime execution role today has `GetWorkloadAccessToken*` but **not** `GetResourceOauth2Token`. P1 adds it, plus `GetSecretValue` scoped to that surface's providers (`bedrock-agentcore-identity!default/oauth2/<prefix>*`). The implementation notes below explain why this scope is narrower than the wildcard first anticipated here.

## Phase-1 implementation notes (learned live, 2026-08-28)

These notes are recorded here because they are properties of AgentCore Identity, not of Linear. The same facts apply to the Jira, Slack, and GitHub `ChannelCredential`s in P7, and none of them can be discovered from a unit test.

**Two deliberate deviations from the P1 text above.**

1. **Per-workspace credential provider, not one provider with per-workspace subjects.** P1 described a single provider under one workload identity. As built, there is one shared workload identity (`abca_linear_oauth`, as designed) but a provider per workspace (`bgagent-linear-oauth-<slug>`), selected by the registry row's `provider_name`. Each workspace authorizes the OAuth app separately, and the provider rotates that workspace's own refresh token. A provider per workspace therefore keeps one workspace's grant, and its revocation, from touching another's. The per-workspace Secrets Manager secret gave the same isolation. The subject is still `linear-workspace:<id>`.
2. **The agent self-mints on both substrates.** The agent does not consume the AgentCore-injected `WorkloadAccessToken` header. It calls `get_workload_access_token_for_user_id` and `get_resource_oauth2_token` through boto3 against its ambient role. AgentCore Runtime and ECS then behave identically, so the substrate-independence claim is testable, not aspirational.

**IAM: the resources that the data plane authorizes against are not the ones you would guess.** Both were found only by a live `AccessDenied`, because a unit test can assert only the ARN that you chose:

- `GetWorkloadAccessTokenForUserId` authorizes against the workload-identity **directory** (`workload-identity-directory/default`), *not* the named identity beneath it.
- `GetResourceOauth2Token` authorizes against **four** resources, all required: the token vault (`token-vault/default`), the specific `oauth2credentialprovider/<name>`, the named workload identity, and the workload-identity directory. IAM names only the first resource that it cannot authorize, so the set stays hidden until each one is granted in turn. It took three successive denials to enumerate the set. Of the four, only the credential-provider ARN can be narrowed.
- `secretsmanager:GetSecretValue` is required, because the vault reads the provider's client secret through the caller's credentials. It is **not** required on the `bedrock-agentcore-identity!*` wildcard that this ADR originally anticipated. **Superseded (2026-09-01).** The secret name embeds the provider, so the grant is scoped to `!default/oauth2/<surface-prefix>*` instead. The wildcard is wider than it reads, for three reasons. These are raw OAuth *client* secrets. `grantMintToken` is applied to roles that execute untrusted repository code. The account's vault already holds a GitHub provider and an unrelated API key beside the Linear ones, with Jira and Slack to come under P7. A leaked client secret mints and refreshes offline, and so survives the revocation that P1 and #812 exist to make actionable. Verified live: the scoped grant still mints, and it is denied the GitHub provider's secret. Per-surface scoping is therefore the rule for P7, not the wildcard.

**A cached grant is keyed by the whole token request, `customParameters` included.** A resolve without the same `customParameters` that were used at consent time returns an `authorizationUrl` ("consent required") even when a valid grant is cached, so every resolve silently degrades to the fallback. Linear needs `actor=app` and `prompt=consent` to consent at all, so both resolvers must always send that identical set. The parameters look redundant on a read, but they are required.

**Consent must be finalized explicitly.** After the user authorizes, the provider's callback exchanges the code and AgentCore redirects the browser to the caller-supplied `resourceOauth2ReturnUrl` with `?session_id=…`. Until `CompleteResourceTokenAuth` is called with that session, the vault keeps reporting "consent required", and polling alone never yields a token. The return URL is therefore required, not cosmetic. ABCA finalizes from the CLI with the operator's own credentials. The hosted consent page only *displays* the session id. This design deliberately avoids a public unauthenticated endpoint that completes OAuth sessions.

**Revocation changes shape on the vault path.** Secrets Manager reported a dead grant as an `invalid_grant` error. The vault reports it as an authorization URL. Detection keyed only on the `invalid_grant` error will miss it. This gap is tracked in [#812](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/812).

**What Phase 1 does not deliver.** The `ChannelCredential` is a workspace-scoped bot identity, so the token cannot attribute work to the human who triggered it. Per-user attribution stays with #245's logs until the unresolved task-user propagation (P6) lands. The vault also does not prevent a provider from revoking a grant. It changes who stores and refreshes the token, not whether the vendor revokes it.
