## Context

ABCA selects a per-repo compute backend through the Blueprint's `compute_type` field (`cdk/src/handlers/shared/repo-config.ts`). Two backends exist today, resolved by `resolveComputeStrategy` (`cdk/src/handlers/shared/compute-strategy.ts`) behind a uniform `ComputeStrategy` interface (`startSession` / `pollSession` / `stopSession`):

- **AgentCore Runtime** (`agentcore`, default). A managed Firecracker MicroVM per session. It is invoked through `InvokeAgentRuntime`. Liveness is inferred from agent heartbeats in DynamoDB plus the FastAPI `/ping` endpoint (`agent/src/server.py`), and the strategy's `pollSession` is a stub that always reports `running`. Constraints: a 2 GB image limit, and no substrate-level suspend API exposed to the orchestrator.
- **ECS on Fargate** (`ecs`). An always-on Fargate task (16 vCPU / 120 GB, ARM64) for repos that exceed AgentCore's limits ([#596](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/pull/596)). It is invoked through `RunTask` in batch mode, which bypasses the HTTP server. Liveness comes from `DescribeTasks`. There is no suspend, so an idle task blocked on an approval wait uses full compute the whole time.

**AWS Lambda MicroVMs** (launched 2026-06-22) is a serverless Firecracker sandbox service that AWS positions explicitly for AI coding agents. It offers VM-level isolation, snapshot-based near-instant launch, **suspend and resume with full memory and disk state preserved** (compute charges stop while suspended), a dedicated JWE-authenticated HTTPS endpoint per instance, lifecycle hooks (`/run`, `/suspend`, `/resume`, `/terminate`), and up to 8 hours per session. It is **not** classic Lambda. The 15-minute function cap does not apply, and the "Lambda: poor fit" verdict in [COMPUTE.md](/sample-autonomous-cloud-coding-agents/architecture/compute) refers to functions, not MicroVMs.

[#645](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/645) proposes adding Lambda MicroVMs as a third `ComputeStrategy`. The fit is strong but not free. Pre-implementation review of the service's lifecycle model found design tensions that this ADR resolves.

### Capability comparison (delta rows only — full matrix in COMPUTE.md)

> Rows marked **verified** were discharged empirically on 2026-07-31 (us-east-1). See `docs/verification/645-p1-lambda-microvm-runbook.md`. That run **refuted** two originally documented constants, which are corrected throughout this ADR: the `runHookPayload` cap (16 KB, corrected to 4 KB) and the claim that `RunMicrovm` accepts a bare image name (it does not).
>
> **Source hierarchy for service facts.** Where sources disagree, the higher tier wins, and the tier is recorded next to the claim:
>
> 1. **Live boundary probe.** A request that the service actually accepted or rejected in this account and Region. It is the strongest tier, and the only tier that can refute the others. Both corrections above came from this tier.
> 2. **Modeled constraints.** The CLI and SDK request schema and the enumerated allowed values (`--generate-cli-skeleton`, `ARM_64`, `ENABLED|DISABLED`). Authoritative about request *shape*, and silent about runtime behaviour.
> 3. **Service developer guide.** This tier includes the guide's sizing and scaling tables. It is authoritative about *semantics* that a probe cannot see, and that is how the memory row was fixed. A probe can show only that 32,768 MiB is rejected as a `minimumMemoryInMiB` value. Only the guide explains that the field is a BASELINE and that the service scales to a 32 GiB peak on its own. A boundary probe is the strongest evidence about a boundary and says nothing about what the boundary *means*.
> 4. **SDK docstrings.** Generated, and demonstrably stale here. `runHookPayload` documents "Maximum: 16,384 bytes" against an enforced 4,096.
> 5. **Launch blogs, skills, and toolkit material.** Orientation only. Never sufficient evidence on its own.
>
> **Omitted API fields mean "service default", never "none".** Two live findings drove this rule: leaving `ingressNetworkConnectors` unset attaches a PUBLIC `HTTP_INGRESS` connector, and leaving `/ready` out of `hooks` makes the image un-creatable once any lifecycle hook is enabled. For any security-relevant field, the desired posture must therefore be **requested explicitly**, and the test must assert the **outcome** (the ARN present in the request, the hook enabled), not the omission (`expect(field).toBeUndefined()`). An omission assertion also passes when the service silently chooses something wider.
>
> On the **memory** row specifically, `CreateMicrovmImage` enumerates the baseline sizes that a base image supports (`[512, 1024, 2048, 4096, 8192]` MiB for `al2023-1`) and rejects anything else. The construct therefore validates against that list at synth. The service's own vertical scaling reaches the 32 GiB / 16 vCPU peak. A deployment does not ask for the peak. The account memory quota (`L-CD1C0CC4`, 1024 GB, "burst up to 4×") is an aggregate across MicroVMs, not a per-VM limit. Do concurrency arithmetic against the PEAK, not the baseline, because the peak is what a busy fleet can consume.

### Design tensions the strategy must resolve

1. **Idle detection is inbound-traffic-based, and the ABCA agent is outbound-only.** MicroVM idle policies suspend when no traffic arrives at the *endpoint*. A busy agent running a 40-minute build receives no inbound traffic and would be suspended mid-work by a naive idle policy. Conversely, "no inbound traffic" is the agent's *normal* state.
2. **No self-suspend.** The agent cannot suspend its own MicroVM from inside. Only an external `SuspendMicrovm` call can. The orchestrator must own suspend decisions, which aligns with the unified liveness model proposed in [#491](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/491).
3. **Snapshots capture state.** The image snapshot is captured once at build time, and every MicroVM resumes from it. Secrets, tokens, and per-task identity must arrive at run time (`runHookPayload`, ≤ 4 KB, or fetched in the `/run` hook), never at image build. CSPRNG reseeding is a consequence of the same property and is scoped to **P3**. The amended note under sub-decision 2 and the risk bullet record why the exposure is negligible today.
4. **Auth tokens are short-lived.** JWE tokens last at most 60 minutes. Any HTTP interaction from the orchestrator to the agent over the endpoint needs token refresh, unlike AgentCore's SigV4 invoke or ECS's no-endpoint model.
5. **The identity delta is narrower than it looks.** Most AgentCore services that ABCA uses are standalone and substrate-portable. Memory is already consumed from ECS through an IAM grant plus `MEMORY_ID` (`EcsAgentCluster`), and Gateway (ADR-019) is portable by design (SigV4 inbound). The one Runtime-coupled piece is the workload-access-token **delivery mechanism** (`runtimeUserId` → `WorkloadAccessToken` request header → `BedrockAgentCoreContext`, used by `resolve_linear_api_token()`), which has no MicroVM equivalent. The ECS backend already has this delta (env-var token delivery). MicroVMs inherit the same posture until the pluggable identity work ([#249](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/249), ADR-016) redesigns the seam.
6. **The service's defaults are not our posture.** Two defaults, both discovered live, differ from it. `RunMicrovm` attaches a **public** `HTTP_INGRESS` connector (and mints a public `*.lambda-microvm.<region>.on.aws` endpoint) when `ingressNetworkConnectors` is omitted. `CreateMicrovmImage` **requires** the `/ready` hook whenever any lifecycle hook is enabled. Neither posture can be reached by leaving a field out. Each needs an explicit control (see sub-decisions 3 and 4).

## Decision

Adopt **AWS Lambda MicroVMs as a third, opt-in `ComputeStrategy` backend** named `lambda-microvm`, selected per repo through Blueprint `compute_type`. AgentCore remains the default. There are five sub-decisions.

### 1. Strategy shape: extend the interface with mandatory suspend/resume

`ComputeType` widens to `'agentcore' | 'ecs' | 'lambda-microvm'` (mirrored in `cli/src/types.ts` and the CLI's inline unions). `SessionHandle` gains a `{ strategyType: 'lambda-microvm', microvmId, endpoint }` variant. The variant carries `microvmId` because every lifecycle API takes only the MicroVM identifier. Those APIs are `suspend-microvm`, `resume-microvm`, `terminate-microvm`, `get-microvm`, and `create-microvm-auth-token`, the last of which is not called in P1–P3 (see sub-decision 3). The variant carries `endpoint` because the endpoint is per-session (minted by `RunMicrovm`) and required for any HTTP interaction from the orchestrator to the agent. Note the naming mismatch. The handle field is `microvmId` (matching `RunMicrovmResponse.microvmId`), while the request key on every lifecycle command is `microvmIdentifier`. The strategy is the only place that translates between the two. The image ARN is deliberately **not** in the handle. Like the ECS task definition ARN, it is deployment-time configuration that `startSession` consumes from the construct-injected environment and records in the session-start log entry for diagnostics. It is not per-session lifecycle state.

**A second, sharper naming mismatch. `imageIdentifier` must be an ARN.** The name suggests that a bare image name is acceptable. `create-microvm-image --name` takes one, and this ADR originally assumed that `run-microvm --image-identifier` would too. It does not. A bare name is rejected with `ValidationException: Malformed ARN - doesn't start with 'arn:'`, and so is `list-microvm-image-builds --image-identifier <name>` (`Invalid ARN format`). The construct therefore resolves an operator-supplied name to its exact `arn:${Partition}:lambda:${Region}:${Account}:microvm-image:${Name}` ARN **once**, the same value to which it scopes the lifecycle IAM grant, and injects THAT as `MICROVM_IMAGE_IDENTIFIER`. There is one derivation and two consumers, so a request field and an IAM resource can never disagree. The strategy validates the invariant and fails fast with the remedy, because the service's own error names neither the env var nor the fix.

The `ComputeStrategy` interface gains **mandatory** `suspendSession(handle)` and `resumeSession(handle)` methods that return a typed result (shaped like `{ supported: false } | { supported: true }`, with the exact type set at implementation time). The widening lands in P3 (see sub-decision 5), in one commit across all three strategies. The codebase idiom is a mandatory method with an explicit stub, not an optional method. No behavioral interface in the codebase has an optional method. `AgentCoreComputeStrategy.pollSession` is already a mandatory explicit stub, not an optional member. The exhaustive-`never` switch convention means that a fourth backend must make a compile-checked decision about its suspend semantics instead of silently falling through a `strategy.suspendSession?.()` feature detection. The agentcore and ecs strategies return `unsupported`, not a silent success. A suspend that silently does nothing would let the orchestrator believe that compute billing stopped when it did not. The orchestrator gates its suspend policy on the typed response, consistent with how `pollTaskStatus` already branches explicitly on `computeType`.

**Poll semantics. The strategy reports, and the orchestrator interprets.** `pollSession(handle)` receives only the session handle and cannot see task state, so the health rules must be where the DynamoDB status is. `SessionStatus` gains a `'suspended'` variant. The strategy maps `GetMicrovm` state mechanically, and the **orchestrator** cross-references that state against the task row. `finalPollState` already uses the same division of labor for ECS (substrate stopped plus a non-terminal DynamoDB status means failed), and `pollTaskStatus` uses it for agentcore heartbeats. The rules are as follows. Substrate `suspended` with task `AWAITING_APPROVAL` is healthy (an orchestrator-intended suspend). `suspended` with any other task status is an anomaly to report, not a reason to fail fast. A terminal substrate state with a non-terminal task status is classified as failed.

**Liveness on this backend is substrate state AND agent heartbeat.** The substrate cross-check above answers one question, "is the VM still there?", and P2 established that it is not sufficient on its own. `GetMicrovm` catches a MicroVM that *died*. It cannot catch a MicroVM that is alive and reporting `RUNNING` while the pipeline **inside the guest** is hung, deadlocked, or was OOM-killed. That state is not hypothetical or self-correcting on this substrate, and the P2 live run narrowed *why* without weakening the conclusion. The service does reap a VM whose run hook FAILS (a 4xx makes it terminate within ~12 s, see sub-decision 2). The P1 evidence for this paragraph (a hook-less image that stays in `RUNNING` indefinitely with no `stateReason`) therefore no longer describes an ABCA image. What the service reaps is a hook *result*. It has no view into the guest afterwards. The surviving, and more realistic, hang case is a `/run` hook that returned **200** and a pipeline that then hung, deadlocked or was OOM-killed behind it. The substrate stays `RUNNING`, the service is satisfied, and nothing else notices. With the substrate check alone, such a task would use the orchestrator's full ~8.5 h poll window, and bill an 8-hour reservation, before the safety net fired.

The in-guest half already exists, but not on every substrate. The only periodic writer of `agent_heartbeat_at` is the server's heartbeat worker, which starts when the uvicorn server spawns a pipeline (AgentCore and Lambda MicroVMs). ECS runs the pipeline without that server, so its task row gets one write at pipeline start and then goes stale on a healthy task. The orchestrator's *reaction* was backend-scoped, because `pollTaskStatus` evaluated staleness for `agentcore` alone. P2 closes that gap by extending the evaluation to `lambda-microvm`. The grace and stale thresholds are the SAME on both. The same pipeline code writes the timestamp at the same cadence, so a backend-specific window would encode a difference that does not exist. The two signals are complementary, not redundant. The substrate check is the crash detector, and the heartbeat is the hang detector. The check remains scoped to task status `RUNNING`, so a VM that is deliberately suspended during an approval wait (sub-decision 2, P3) is not read as a dead one. `ecs` must stay out, because it has no periodic writer and a staleness check would kill healthy ECS tasks. ECS liveness comes from `DescribeTasks`, which reports a real container exit *with an exit code* (OOM-kill included). The ECS poll block already interprets that exit with its own patience counters.

The service's `MicrovmState` enum has **six** members, not three, so the mapping is stated exhaustively (one line of rationale each, mirrored in the strategy's doc comment):

| `MicrovmState` | `SessionStatus` | Why |
|---|---|---|
| `PENDING` | `running` | Still booting, in the same way that ECS's `PENDING` and `PROVISIONING` map to `running`. |
| `RUNNING` | `running` | — |
| `SUSPENDING` | `suspended` | Already on its way to frozen. Reporting `running` would tell the orchestrator that compute is still progressing when it is not. Both suspend states map to a report that the orchestrator treats as benign or anomalous depending on task status, never as failure. **Never observable in practice**, because suspend reached `SUSPENDED` in under 1 s live. It is mapped for completeness, and nothing may *wait* for it. |
| `SUSPENDED` | `suspended` | — |
| `TERMINATING` | `completed` | Terminal-bound and carries no exit code, so "the substrate is gone" is all that the strategy can say. |
| `TERMINATED` | `completed` | Success or failure is the orchestrator's decision, because it cross-references the DynamoDB status. **This is the terminal signal that fires in practice**, not `NotFound` (see below). |
| *unrecognized* | `running` | A future service enum addition must never fail a healthy task. The strategy warns and keeps polling. |

**`GetMicrovm` `ResourceNotFoundException` maps to `completed`, but as a LATE fallback.** This mapping deliberately diverges from `ecs-strategy`, where `DescribeTasks` returning no task maps to `failed`. ECS keeps stopped tasks describable for roughly an hour, so a missing task there is anomalous. A MicroVM is eventually reaped from the control plane **by design**, so `failed` would fail tasks that finished cleanly.

The live run corrected the *timing*, not the mapping. `NotFound` is **not the near-term terminal signal**. A terminated MicroVM reported `TERMINATING` at +1 s and `TERMINATED` at +3 s, and it was **still `TERMINATED` ~10 minutes later** and at every subsequent checkpoint. `ResourceNotFoundException` was never observed in that window. The branch that fires in practice is therefore `TERMINATED → completed` in the table above. The `NotFound` rule covers only a VM reaped after a long gap (a poll resumed after a crash, or a stranded-task reconciler sweep). Both are required, and neither substitutes for the other. Without the `TERMINATED` row, the orchestrator would poll a finished VM until its safety net fired. Without the `NotFound` rule, a late sweep would classify a cleanly finished task as a poll error.

The divergence is safe because it does not weaken detection. The orchestrator still fails the task when a terminal report arrives while the DynamoDB status is non-terminal, so a real mid-run disappearance is caught. It receives the substrate-failure classification instead of a misleading poll error. That cross-check acts on a status read earlier in the same poll cycle, so the orchestrator **re-reads the task row before failing**. The normal shutdown order is "agent writes terminal status → agent exits → VM terminates", and a stale read would otherwise turn that order into a spurious failure. ECS gets the same protection from a five-consecutive-poll patience counter.

Neither the mapping nor the NotFound rule is a health decision. Both are mechanical restatements of substrate state, and that keeps the "strategy reports, orchestrator interprets" split intact.

Normative requirements (EARS, per [ADR-020](/sample-autonomous-cloud-coding-agents/decisions/adr-020-ears-requirements-syntax)):

- When a task's Blueprint sets `compute_type: 'lambda-microvm'`, the orchestrator shall resolve the `LambdaMicrovmComputeStrategy` via `resolveComputeStrategy`.
- When `startSession` is invoked, the strategy shall call `RunMicrovm` with `maximumDurationInSeconds` set to 28 800 (the service maximum, matching AgentCore's 8-hour session cap and sitting inside the orchestrator's ~8.5 h safety-net poll window).
- When `startSession` is invoked, the strategy shall pass a fully-qualified MicroVM image ARN as `imageIdentifier`.
- If the configured image identifier is not an ARN, then the strategy shall fail the session start with an error naming the environment variable and the redeploy remedy, before performing any AWS call.
- When `startSession` returns, the orchestrator shall persist the MicroVM handle (`microvmId`, `endpoint`) in the task row's `compute_metadata` (the field `cancel-task.ts` already reads ECS handles from).
- The strategy shall omit `idlePolicy` on every `RunMicrovm` call, in every phase.
- The orchestrator shall be the sole initiator of suspension, via `suspendSession`.
- When `pollSession` observes MicroVM state `SUSPENDED` or `SUSPENDING`, the strategy shall report `suspended` without interpreting task state.
- When `pollSession` observes MicroVM state `TERMINATED` or `TERMINATING`, the strategy shall report `completed` (the observable terminal state persists for at least ~10 minutes, so `completed` shall not depend on the MicroVM being reaped).
- When `pollSession` observes a MicroVM state it does not recognize, the strategy shall report `running`.
- If `GetMicrovm` reports that the MicroVM does not exist, then the strategy shall report `completed`.
- If the strategy reports a terminal substrate state while the task's DynamoDB status is non-terminal, then the orchestrator shall re-read the task row and, if it is still non-terminal, classify the task as failed with a substrate-failure remedy.
- If the strategy reports `suspended` while the task's DynamoDB status is not `AWAITING_APPROVAL`, then the orchestrator shall surface an anomaly event and shall not fail-fast the task.
- While a `lambda-microvm` task's DynamoDB status is `RUNNING`, if the task's `agent_heartbeat_at` is stale (or absent past the grace window) by the same thresholds the orchestrator applies to `agentcore`, then the orchestrator shall treat the session as unhealthy and stop polling. The substrate `GetMicrovm` check shall remain the crash detector, and the heartbeat shall be the in-guest hang detector.
- The task-detail API response shall include `agent_heartbeat_at`, and the CLI shall surface it while the task is non-terminal (P2r2-F11: the field drove the orchestrator's hang detector but was never projected, so no operator could observe the signal, and its invisibility produced a wrong verification conclusion).
- The task-**summary** API response (`GET /v1/tasks`) shall also include `agent_heartbeat_at`, and `bgagent list` shall render it as an age column. Extending the field to the list response is a deliberate widening of the requirement above, not an incidental one. The detail-only projection makes liveness a per-task question, and an operator who checks a fleet of tasks one `bgagent status` at a time is how the hung task that P2r2-F11 describes went unnoticed. The list view uses the same suppression rule as the detail view (terminal tasks and never-beaten tasks render a placeholder), so the two views cannot disagree.
- If `suspendSession` or `resumeSession` is invoked on a strategy that does not support suspension, then the strategy shall return an explicit unsupported result.
- When the agent process reaches a terminal state, the agent shall exit.
- When the orchestrator finalizes a `lambda-microvm` task, the orchestrator shall call `terminate-microvm` (termination shall not rely on any substrate timeout, and shall not rely on the MicroVM self-terminating, because it does not).

*On the omitted `idlePolicy`.* If the block is present, all three fields are required, so omission is the unambiguous disabled state that the invariant test asserts. The omission deliberately forgoes `suspendedDurationSeconds`, which is *inside* `idlePolicy` and cannot be set without re-enabling the traffic-idle machinery. The suspended-state bound is therefore `maximumDurationInSeconds` plus orchestrator termination and the stranded-approval reconciler (see sub-decision 2). A tighter substrate-level suspended-TTL remains available later as an additive `idlePolicy` change if operators want it. *On the fixed `maximumDurationInSeconds`.* No wall-clock task budget exists in the platform (budgets are `max_turns` and `max_budget_usd`), so the value is parity with AgentCore's 8 h cap, not derived policy. A Blueprint override can be added later if a real need appears.

### 2. Lifecycle: suspend/resume reconciled with the agent-owned approval poll

The main economic gain is suspend during **HITL approval waits** (Cedar approval gates, [CEDAR_HITL_GATES.md](/sample-autonomous-cloud-coding-agents/architecture/cedar-hitl-gates)). While a task waits on a human decision, the MicroVM is suspended, and it is resumed when the decision arrives. Compute charges stop, and memory and disk state (the cloned repo and warm build caches) is preserved. Under Cedar decision #6 the approval window is bounded (default 300 s, ceiling 1 h, and a timeout means deny), so the saving per gate is bounded at ~1 h of compute. That saving is real at 16 vCPU, and it makes any future extension of gate ceilings (the off-hours posture that §14.8 deliberately defers) cheap on this backend.

The handshake must respect the existing approval mechanics. The agent **discovers decisions itself** by polling DynamoDB (`_poll_for_decision`, monotonic timeout), the approve or deny Lambda writes only the decision rows, and `AWAITING_APPROVAL` holds the concurrency slot (Cedar decision #7). Nothing "delivers" an approval to the agent, and suspension freezes the agent's monotonic clock. The design is therefore:

- **Suspend is orchestrator-owned.** The orchestrator's durable poll observes `AWAITING_APPROVAL` on a `lambda-microvm` task and calls `suspendSession` after a grace period, and only when the gate's remaining window exceeds the grace period plus the resume overhead (suspending a 30 s gate is pure loss). Suspend is a policy decision on a poll observation, not a user action.
- **Resume is inline in the approve and deny Lambdas, with the orchestrator poll as backstop.** After the transactional decision write commits, `ApproveTaskFn` and `DenyTaskFn` load the MicroVM handle from the task row's `compute_metadata` through a post-commit strongly consistent `GetItem`. The handle is persisted at session start, in the same field from which `cancel-task.ts` reads ECS handles. The Lambdas then call `resumeSession` **best-effort**. On failure they log a warning and write a resume-orphan task event. The decision response never fails on a compute error, because the decision row is already durable. The orchestrator poll reconciles. When a decision row is present and the MicroVM is still `SUSPENDED`, the poll retries the resume, which is idempotent.

  *Why inline and not poll-only. The codebase has a precedent.* Resume-on-approve is structurally identical to task cancellation. Both are user-initiated, latency-sensitive actions whose purpose is an immediate compute-lifecycle side effect. `cancel-task.ts` already resolves this exact tension. The API-plane handler invokes ECS `StopTask` or AgentCore `StopRuntimeSession` inline and best-effort, with the conditional IAM wired in `task-api.ts`. A failed stop logs a warning and the state transition stands. A `task_cancel_compute_orphan` event is written when no stoppable compute handle exists (`reason: missing_runtime_handle`). The resume path goes one step further than the precedent and also writes the orphan event on *failed* resume calls. A failed resume strands a suspended VM that awaits a decision, a stronger liveness consequence than a failed stop of an already-cancelled task. The alternative (orchestrator-poll-only resume) keeps a single lifecycle owner but pays up to a full poll interval (~30 s) of latency on every approval, and the single-owner argument was already considered and declined for cancel. `approve-task.ts` is deliberately minimal today (security-critical ownership comparison, Cedar finding #6). The resume call is therefore added *after* the transaction commits, cannot alter the decision outcome, and carries one conditional `lambda:ResumeMicrovm` grant, the same trade in exposure that the cancel handler accepted in review.
- **Timeout under freeze. The agent re-bases on the wall clock that it already owns.** The agent's monotonic gate timer freezes while suspended, so resuming near the deadline is not enough. The frozen timer would still hold its remaining budget and fire the deny minutes *after* the user-visible window. That late deny would collide with the approval row's TTL (`created_at + timeout_s + 120s`) and trigger the "row reaped → stranded" fallback on a healthy gate. Instead, the gate expires at **`min(monotonic budget, created_at + timeout_s)`**, evaluated on each poll iteration and on `/resume`. This is not a new principle. Cedar decision #6 is already "min wins" for timeouts. The wall-clock deadline is already durable in the approval row that the agent itself writes (`created_at` is in the agent's own clock domain, so there is no skew). §13.12's late-approval race fix already establishes that the durable row is authoritative over the agent's local timer. Deny authority stays agent-side, and the race protection (the conditional `TIMED_OUT` write plus the ConsistentRead re-read) is untouched. The orchestrator's resume at `deadline − margin` is only the wake-up mechanism and has no correctness role.
- **Backstops, not mechanisms.** `maximumDurationInSeconds` (mandatory on every `RunMicrovm`, pinned at 28 800 s, see sub-decision 1) is the substrate hard limit that bounds running **and** suspended time. The orchestrator's finalization `terminate-microvm` is the active cleanup path. The stranded-approval reconciler retains its role for orphaned waits. No `idlePolicy`-based bound is used in any phase (see sub-decision 1's omit-`idlePolicy` invariant).

  **The active terminate is still mandatory on the SUCCESS path, and P2 clarified why.** P1 concluded without qualification that "nothing self-terminates". A hook-less MicroVM reached `RUNNING` in 12 s and stayed there with no `stateReason` through every checkpoint. P2 refuted that conclusion *for the failure path only*. With `run: ENABLED`, a run hook that answers 4xx makes the **service** terminate the VM within ~12 s, with `stateReason: "Run lifecycle hook returned HTTP status 400. Please check your hook endpoint and application logs for more details."`. After that, `suspend-microvm` correctly refuses the VM. That behaviour is a real improvement in cost posture and a direct benefit of declaring hooks (see also the failure-path row in the phasing table, sub-decision 3).

  It does **not** relieve the orchestrator of anything, because the two cases are disjoint. The service reaps a hook *result* that it rejected. It has no view of the guest once the hook returned 200. A task that starts normally, which is the overwhelming majority, therefore has no service-side reaper at all, and a VM whose pipeline finished, crashed after `/run`, or hung is reaped only by `TerminateMicrovm`. A leaked handle therefore remains a cost incident that bills until the 8 h cap. Only the "the guest rejected its own payload" case now cleans itself up.
- **Concurrency slot stays held** during suspend. Cedar decision #7's rationale ("container alive, consuming memory") weakens under suspend. The harder replacement rationale is "AWS counts `SUSPENDED` MicroVMs toward the account memory quota, so releasing ABCA's slot would not free real capacity", and it is **undischarged**. The suspended VM stayed in `list-microvms` at every checkpoint, but that proves only that it is *listed*. `L-CD1C0CC4` (1024 GB, account-scoped) exposes no `UsageMetric`, `AWS/Usage` carries only `CallCount` per API, and no MicroVM memory metric exists in any namespace. Consumption is therefore **not observable safely**, and proving it would need a large concurrent fleet. The conclusion (hold the slot) stands as the conservative choice, not as a verified fact. Size the arithmetic against the 32 GiB **peak**, not the 8 GiB baseline. A busy fleet scales up, so the peak is what competes for the account quota.

The agent's `/suspend` hook flushes progress events (durable writes before returning 200, within the 60 s hook budget). `/resume` reseeds CSPRNGs and refreshes cached credentials.

**Amended (P2 review). CSPRNG reseeding is P3 scope, and the P2 exposure is negligible.** The original EARS requirement below implied that a `/run`-time reseed had to land with P2. It did not, and shipping P2 with the requirement asserted but unmet was itself the defect. The measured exposure changed the scoping:

- The only consumer of a non-cryptographic PRNG in `agent/src` is `progress_writer.py`'s `getrandbits(80)`, used for the random half of a **ULID**. `os.urandom` and `secrets` are not seeded from the snapshot at all, and nothing in the agent derives a key, token, or nonce from `random`.
- That ULID is a DynamoDB **sort key under a `task_id` partition**. A collision therefore needs two events in the *same task* at the *same millisecond* with the same 80 random bits. Identical PRNG state across two MicroVMs restored from one snapshot does not produce that collision, because the events are in different partitions. The worst case is a duplicate progress event within one task, not a security boundary.
- The snapshot's PRNG state exposes no credential. Build-role credentials are kept out of the snapshot structurally, because the build hooks make zero AWS calls and `boto3.DEFAULT_SESSION` is therefore never populated (see `_aws_silent_log`). Per-task credentials arrive through `platform_config.agent_session_role_arn` at `/run`.

The reseed therefore moves to P3 alongside `/suspend` and `/resume`. A *resumed* VM continues with the exact PRNG state that it was frozen with, repeatedly, so in P3 the reseed is necessary and no longer theoretical. P3 must reseed on both `/run` and `/resume`, and must not treat the ULID as the only consumer. Any future use of `random` for anything security-relevant needs the reseed in place first.

Normative requirements (EARS):

- While a `lambda-microvm` task is in `AWAITING_APPROVAL` and the gate's remaining window exceeds the configured grace period plus resume overhead, the orchestrator shall call `suspendSession` after the grace period.
- When the approve or deny Lambda commits a decision for a `lambda-microvm` task, the Lambda shall load the MicroVM handle from `compute_metadata` and call `resumeSession` best-effort.
- If the inline resume fails, then the Lambda shall record a resume-orphan task event and shall still return the decision outcome.
- While a decision row exists and the MicroVM remains `SUSPENDED`, the orchestrator shall retry `resumeSession`.
- While a `lambda-microvm` task waits on an approval gate, the agent shall evaluate gate expiry as the earlier of its monotonic budget and the row's wall-clock deadline (`created_at + timeout_s`), on each poll iteration and on `/resume`.
- If gate expiry is reached without a decision, then the agent shall deny.
- If no decision arrives by the gate's wall-clock deadline minus the resume margin, then the orchestrator shall resume the MicroVM so the agent can evaluate expiry and fire the deny agent-side.

### 3. Packaging: same agent image source, new build path

The existing agent container (`agent/` Dockerfile, already ARM64) is repackaged as a zip plus Dockerfile artifact in S3 and built into a versioned `MicrovmImage` through `CreateMicrovmImage`. The agent runs its existing FastAPI server (`agent/src/server.py`), because the MicroVM path uses the HTTP entrypoint like AgentCore, not ECS's batch bypass. The server also serves the runtime lifecycle hooks (`/run`, `/suspend`, `/resume`, `/terminate`) and the `/ready` and `/validate` build hooks, all on the same port that it already listens on (8080, declared as the image's `hooks.port`). Runtime hooks are fast-notification only (1–60 s). `/run` validates the payload and starts the pipeline **asynchronously**, mirroring how the agent loop already runs in a background thread behind `/ping` on AgentCore.

**Hook phasing, corrected. `/ready` and `/run` are both P1.** The original plan split *declaring* a hook from *serving* it, with `/run`'s declaration in P1 and its implementation in P2. Live verification proved that this split is **not a reachable service state**, on two independent counts:

- `CreateMicrovmImage` rejects an image that enables any lifecycle hook without `/ready`: *"The ready (/ready) MicroVM image hook must be enabled when any MicroVM lifecycle hook (run, resume, suspend, or terminate) is enabled."* A P1 image that declares only `/run` is therefore **not creatable**.
- With `/ready` added but unserved, both chipset builds fail: *"Ready hook check failed: the application returned a client error (HTTP 4xx) response."* A declared hook must therefore be served in the same phase.
- An image with **no** hooks at all, the only other creatable shape, cannot receive a payload: *"The run hook must be enabled in the MicroVM image to pass the run hook payload."* Deferring hooks entirely therefore also defers the whole payload-delivery channel.

The phasing is therefore:

| Hook | Declared by | Served by the agent | Notes |
|---|---|---|---|
| `/ready` | **P1** (construct enables `hooks.microvmImageHooks.ready`) | **P1** | MANDATORY, not a quality improvement (see above). A 200 proves that uvicorn is bound and that `server` imported cleanly (pulling in `pipeline` → `runner` → the policy engine), so a missing policy file fails the BUILD instead of the first task. **Since P2-F5 it also WARMS the snapshot.** The service waits for the hook's 200 before it captures the snapshot, so this hook is the only place where a warm page can be created, and the 225 MiB `claude` binary was cold in the snapshot (see the P2-F5 correction below). A required warm-up failure answers 503, so a snapshot that cannot exec the agent's own CLI fails the image build instead of every task. The hook still makes ZERO AWS calls, logging included (a `--version` exec is neither an AWS call nor a network call). |
| `/run` | **P1** (construct sets `hooks.microvmHooks.run`) | **P1** | The payload-delivery channel. Must be served in P1 because `/ready` forces hooks to exist at all, and a hook-less image cannot accept `runHookPayload`. Since P2 it is also the **platform-configuration** channel (see "Platform configuration delivery" below). |
| `/validate` | **P2** (construct sets `hooks.microvmImageHooks.validate`) | **P2** | An **image** (build-time) hook, and a **shallow self-check only**: server alive, hook routes registered, interpreter and contract sanity. It runs under the BUILD role, which deliberately holds no Bedrock, Secrets Manager, or DynamoDB grants, so it must make **zero AWS API calls** and must not touch credential resolution. The "deeper warm-up assertions (Bedrock reachability, Memory access, tool availability)" that this ADR originally assigned here are **not implementable**. Every one of them would get `AccessDenied` and fail every image build. They belong to the first task's own error handling. 200 when the checks pass, 503 while still initialising. |
| `/terminate` | **P2** (construct sets `hooks.microvmHooks.terminate`) | **P2** | Best-effort final flush: a final structured log line, then 200. The 200 is unconditional, inside the hook budget, even with nothing running. The hook must **not** write terminal task status and must not join the pipeline thread. The orchestrator finalizes the task and *then* calls `TerminateMicrovm`, so a terminate hook that wrote a status would race that finalization and could overwrite the real outcome. There is nothing buffered to flush. `_ProgressWriter` does a synchronous `put_item` per event, so durability is per-write. "Always 200" also covers the BODY. The handler reads the raw request, not a typed model, because a typed body is validated before the handler runs and would answer 422 to malformed JSON, which would report a hook failure on a successful teardown. The hook is safe to declare because `TerminateMicrovm` removes the VM with or without in-guest cooperation. **Correction (P2-F8).** The service sends `microvmId: ""` on this hook, unlike `/run` where it is populated. An empty id is therefore expected and normal, and this hook cannot join the guest record to the control-plane one. `/run`'s accepted line carries that correlation instead. |
| `/suspend`, `/resume` | **P3** | **P3** | Declaring a runtime hook the agent does not serve fails the corresponding lifecycle transition, so each is declared only in the phase that implements it. P1 termination is the orchestrator's `TerminateMicrovm`, which needs no in-guest cooperation. |

The consequence replaces the original "a P1-built MicroVM image is not runnable end to end". **A P1 image is creatable, launchable and payload-deliverable, but carries no smoke-parity guarantee.** P1 delivers the strategy, the construct, the roles, buckets, and connectors, the image resource, the packaging script, and the `/ready` and `/run` endpoints. A `lambda-microvm` task can therefore start a MicroVM and hand it a payload. P1 has **not** established anything that P2 owns: AgentCore Memory grants and `MEMORY_ID` delivery, the agent's non-secret env parity inside the snapshot, egress specifics from a running MicroVM, and heartbeat and progress behaviour end to end. No run from clone through change to PR has happened on this substrate. P2 ("smoke parity") is the phase that closes that gap. The construct and the packaging script both report this at synth and run time (`abca:microvm-image-p1-smoke-unverified`), so an operator cannot mistake a launchable substrate for a verified one.

**The `AWS::Lambda::MicrovmImage` L1 enforces the API's enums (P2-F2, live 2026-08-06).** This finding closes the one item that P1 left explicitly open, and it contradicts the construct's own stated reasoning. CloudFormation's generated types make `cpuConfigurations[].architecture` and all four `hooks.*` fields plain strings and document no allowed values. P1 concluded from this that the CloudFormation interface takes a *hook path* while the API takes an `ENABLED`/`DISABLED` flag, and that both were correct for their own interface. CloudFormation refused the change set at **early validation**, on five values. The stack was never touched, so there was no rollback and no runtime symptom to trace back:

```
/aws/lambda-microvms/runtime/v1/run is not a valid enum value. Supported values: [DISABLED, ENABLED]
  (at /Resources/…/Properties/Hooks/MicrovmHooks/Run)          … and the same for Terminate, Ready, Validate
arm64 is not a valid enum value. Supported values: [ARM_64]
  (at /Resources/…/Properties/CpuConfigurations/0/Architecture)
```

There are three consequences. First, the CloudFormation interface is **identical** to the API interface, and the packaging script (`--cpu-configurations '[{"architecture":"ARM_64"}]'`, `--hooks '{"microvmHooks":{"run":"ENABLED",…}}'`) was correct from the start. Second, the "CDK-managed (recommended)" bootstrap path was **non-functional** for the whole of P1 and P2, and the out-of-band `--create-image` script was the only working path. No unit test, `cdk synth` or cdk-nag rule could detect the defect, because the types accept any string. Third, **hook paths are not configurable on either interface**. The service calls fixed well-known routes. The build and run logs prove it, because they POST to exactly the `/aws/lambda-microvms/runtime/v1/*` paths that the agent serves. The route constants in the construct are therefore an agent-side cross-package contract ONLY and must never be sent as property values again. One more item was discharged in passing: the `microvmImageHooks` property name and nesting are correct. CloudFormation resolved `…/Hooks/MicrovmImageHooks/Ready` and objected only to its value.

**A snapshot is only as warm as the pages touched before it was captured (P2-F5, live 2026-08-07).** This defect stopped the P2 smoke run one step short of a pull request. It is a property of the substrate, not a bug in any one file. Every task failed at turn 0, reproducibly:

```
TimeoutExpired: Command '['claude', '--version']' timed out after 10 seconds
```

The binary was fine. In the identical image, locally, `claude --version` answers `2.1.191 (Claude Code)` in under a second. The binary is a **225 MiB (236,305,136-byte) statically-linked ELF** that nothing had exec'd before the snapshot was taken. On a guest restored ~50 s earlier, the first `exec` therefore had to fault all of those pages in from lazily restored storage, and 10 s was not enough. `/ready` existed so that "the snapshot is taken with a warm server". The snapshot was warm for uvicorn and cold for the binary that does all the work.

Both halves of the fix are kept, because they answer different questions. `/ready` now **exec's the heavyweight binaries before returning 200** (`claude` required, `git` and `node` best-effort). That exec is the only mechanism that can make the shipped snapshot warm. The hook's own budget rises to 300 s, well inside the 3600 s build-hook window, because the hook now does work whose duration is a cold `exec`. Two structural rules bound that work, because **per-command timeouts do not compose**. First, the required command runs FIRST with its own budget, so no best-effort warm-up can starve the command that decides whether the snapshot is usable. Second, the best-effort commands then SHARE the remainder of a total warm-up ceiling that sits inside the hook budget with margin (240 s against 300 s). Without these rules, three commands at 120 s each would take 360 s, and the fix for a runtime failure would produce a build failure instead. A single hung optional command could also hold up a 200 that the required warm-up had already earned. Separately, the version probe's timeout goes from 10 s to 60 s. A probe that exists to print a version string into a log line gains nothing from a tight bound and loses the whole task when the bound trips. This finding generalises to a rule, and for that reason it belongs in the ADR and not only in a comment. **On this backend, a first-touch cost that other substrates pay during container start is deferred to the first task instead.** Anything large and lazily loaded is therefore a turn-0 hazard unless it is touched in `/ready`.

**Payload delivery** reuses the ECS strategy's S3-pointer pattern, adapted to `runHookPayload` (**≤ 4 KB**, measured, see below). Payloads that fit are sent inline. The strategy uploads the rest to a platform payload bucket and puts the S3 URI in `runHookPayload` in place of the payload itself. The bucket follows the ECS payload bucket pattern in `ecs-agent-cluster.ts`: orchestrator write access, compute-role read-only access scoped to the bucket, and lifecycle expiry on objects. The MicroVM **execution role** holds the read grant, exactly as the ECS task role does today. Since P2 the hook body also carries `platform_config` in both branches, so `runHookPayload` is never *only* the URI (see the canonical shapes below).

The cap is **4 096 bytes**, not the 16 384 that the SDK documents. An exact measurement shows that 4 096 passes and that 4 097 is rejected with *"Value at 'runHookPayload' failed to satisfy constraint: Member must have length less than or equal to 4096"*. Two consequences follow. First, the original threshold would have inlined every envelope between 4 097 and 16 384 bytes, and the service would have rejected all of them. Second, and more structurally, **the S3-pointer path is now the dominant one, and inline is the exception.** A hydrated task payload (prompt, issue thread, and repo context) almost always exceeds 4 KB, so "small payloads ride inline" describes tiny repo-less prompts, not the common case. The payload bucket is therefore a required part of every normal task, not a rarely exercised overflow path. Its lifecycle rule (`MICROVM_PAYLOAD_TTL_DAYS`) and the execution role's read grant are required for normal operation, not edge-case plumbing.

**Canonical wire shapes.** There are three, and the producer (`lambda-microvm-strategy.ts`) emits exactly these:

| Where | Exact shape |
|---|---|
| `runHookPayload`, inline branch | `{"agent_payload": {…}, "platform_config": {…}}` |
| `runHookPayload`, pointer branch | `{"agent_payload_s3_uri": "s3://…", "platform_config": {…}}` |
| the object at that S3 URI | `{…agent_payload fields…, "platform_config": {…}}`. The payload's own fields are at the TOP level, with the config merged in beside them |

Two asymmetries are deliberate and must not be "tidied" without changing both sides. First, **the S3 object is not the envelope**. The payload's fields are at the top level (that is what P1 uploaded, before `platform_config` existed), not nested under an `agent_payload` key. Second, **`platform_config` is duplicated** on the pointer path, once beside the pointer and once inside the uploaded object. The duplication costs a few hundred bytes. In return, the config is reachable from whichever end of the fetch a reader looks at. That matters because the config is the agent's only substitute for an env block.

The agent's reader is deliberately more permissive than this contract. It also accepts an S3 object shaped like the envelope (`agent_payload` nested), and `platform_config` present in only one of the two places (the fetched object wins, and the hook body is the fallback). These allowances are **defensive compatibility** for the independent deploy cadences of a snapshot image and the orchestrator Lambda. They make a tolerant reader, not an alternative contract. A producer must emit the three shapes above.

**Platform configuration delivery (P2) is payload-sourced, allowlisted, and fail-closed.** The other two backends hand the agent its non-secret platform env at launch, as AgentCore Runtime env vars or ECS container overrides. This substrate has no equivalent. A MicroVM starts from a **snapshot**, so its process environment is whatever was frozen at *image build* time, and every MicroVM launched from that image version replays it. Putting the deployment's identifiers into the snapshot would make them **version-frozen**. A redeploy that renames a table, adds a bucket or rotates the session role would leave every existing image version describing a deployment that no longer exists, and the drift would appear as a task-time `ResourceNotFound`, not a deploy-time error. The values therefore travel with the task. `platform_config` is a SIBLING of the payload. It is beside `agent_payload` in the inline branch, beside `agent_payload_s3_uri` in the pointer branch, and merged in beside the payload's own fields inside the S3 object (the canonical shapes above give each one exactly). The agent installs its snake_case keys into `os.environ` as their UPPER_SNAKE equivalents. A payload value therefore **wins** over any pre-existing or image value, because the orchestrator describes the live deployment and the snapshot describes a past one. `platform_config` carries **non-secret identifiers only** (table and bucket names, secret ARNs, the session-role ARN). Secrets are still fetched at `/run` time from Secrets Manager with those ARNs, so the requirement above that the snapshot stay secret-free is untouched. Per-task fields, such as `memory_id`, stay inside `agent_payload`. `platform_config` configures the *process*, and `agent_payload` describes the *task*.

Two rules make it safe. First, **the allowlist fails closed**. The agent installs a fixed set of keys and *rejects the entire run* (HTTP 400, nothing spawned, not one key installed) if the block carries anything else. These values become environment variables of the process that spawns the agent's tool subprocesses, so an unrecognised key is an attempt to set an arbitrary variable in the agent (`AWS_ENDPOINT_URL`, `LD_PRELOAD`, `PATH`, …). That is an injection attempt, not a forward-compatibility gap, and for that reason unknown keys are refused and not filtered out. Second, **installation happens before any credential or pipeline initialisation** on the hook path. The very next step reads `GITHUB_TOKEN_SECRET_ARN` to resolve the GitHub token and `AGENT_SESSION_ROLE_ARN` to scope the task's credentials, so a later installation would silently resolve the whole task against the snapshot's frozen env. The one call that must precede installation is the S3 payload fetch, because the config is *inside* the fetched object. That fetch therefore runs on the ambient compute role through the attributed platform client, and it is the ONLY such call. The same rule covers **logging**, so every `/run` log line before the install is stdout-only. The CloudWatch writer would otherwise resolve credentials and pin them in a boto3 default session (credentials only, because clients still re-resolve the region) from whatever a snapshot happened to contain, which is the build-hook defect one phase later. Nothing is lost. In the intended deployment there is no baked `LOG_GROUP_NAME`, so those lines would have gone to stdout anyway, and the reason for every pre-install rejection also travels in the structured 4xx/5xx body that the service reports. A **required subset** (task table, task-events table, GitHub token secret ARN, session-role ARN) is rejected as `…_INCOMPLETE` when missing or blank. That is a distinct wire code from the `…_INVALID` allowlist rejection, because the remedies differ (deployment wiring versus a producer bug). A `/run` envelope with *no* `platform_config` at all is still accepted, with a loud warning. The image snapshot and the orchestrator Lambda deploy on independent cadences, and a new image must not require an orchestrator deployed at the same instant. The key set is a cross-package contract in `contracts/constants.json` (`microvm_platform_config`), consumed by the agent's `/run` hook and produced by the orchestrator. `scripts/check-constants-sync.ts` enforces its shape and required-subset invariants.

**No HTTP path from the orchestrator to the agent exists in P1–P3.** The payload arrives through the `/run` hook and all agent work is outbound, so **no JWE auth tokens are minted at all**. Token minting (and its ≤ 60 min TTL refresh problem) is deferred until a real consumer exists, for example operator shell access ([#391](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/391)). The `endpoint` stays in the `SessionHandle` because it is per-session state that such a consumer will need. The service default differs, however. Omitting `ingressNetworkConnectors` on `RunMicrovm` attaches a **public** `HTTP_INGRESS` connector, so the strategy passes the Lambda-managed `NO_INGRESS` connector explicitly on every launch (see sub-decision 4's security table).

**Constraint accepted.** The configured **baseline is 8 GiB RAM / 4 vCPU**, and the service scales vertically to a **32 GiB / 16 vCPU peak** on its own, with 32 GB of disk. Capacity is therefore baseline-priced with 4× burst headroom, which suits the bursty compile-and-test shape of an agent task. The SUSTAINED ceiling is still 32 GiB, so repos that motivated the 120 GB ECS sizing stay on `ecs`. The construct configures and validates the baseline. A deployment does not ask for the peak.

Normative requirements (EARS). **Each requirement's own `(Pn)` tag is authoritative.** There is no blanket phase for the list. The tags are per-requirement because the original list *was* split between P1 and P2 on the assumption that a hook could be declared in one phase and served in a later one. The service does not permit that (see the phasing table above), so the hook-serving requirements moved into P1, while the P2 items below arrived with the P2 hooks and `platform_config`:

- (P1) The image build shall not embed secrets, tokens, or per-task identity in the snapshot.
- (P1) If the task payload exceeds the 4 KB `runHookPayload` limit, then the strategy shall upload the payload to the platform payload bucket and pass its S3 URI in `runHookPayload` in place of the payload (from P2, alongside `platform_config`).
- (P1) The MicroVM execution role shall hold read-only access to the payload bucket, scoped to that bucket.
- (P1) Where no ingress is configured for a deployment, the strategy shall pass the Lambda-managed `NO_INGRESS` network connector on every `RunMicrovm` call (the field shall not be omitted).
- (P1) Where the image enables any MicroVM lifecycle hook, the image shall also enable the `/ready` hook and the agent shall serve it.
- (P1) When the `/run` hook receives the task payload, the agent shall validate it, start the pipeline asynchronously, and return HTTP 200 within the hook budget.
- (P1) If the `/run` hook payload cannot be resolved to a task payload, then the agent shall reject the hook with a client error and shall not start a pipeline.
- (P1) The agent shall not execute the clone→verify→PR pipeline on the hook path.
- (P1) The agent shall resolve credentials at `/run` time.
- (P1) Where a deployment configures a MicroVM image before smoke parity is verified, the platform shall warn that the backend has no smoke-parity guarantee.
- (P2) Where the image declares the `/validate` build hook, the agent shall serve it.
- (P2) The `/validate` hook shall make no AWS API calls.
- (P2) When the `/run` hook receives `platform_config`, the agent shall install only allowlisted keys into the environment before pipeline initialization.
- (P2) If `platform_config` carries a key that is not on the allowlist, then the agent shall reject the run with a 400 and shall install none of the block's keys.
- (P2) If a required `platform_config` key is missing, then the agent shall reject the run with a 400.
- (P2) Where a `platform_config` value and an image-baked environment value disagree, the agent shall use the `platform_config` value.
- (P2) Until `platform_config` is installed, the `/run` hook shall make no AWS API call other than the payload fetch, and shall log to stdout only.
- (P2) Where the image declares the `/terminate` hook, the agent shall return 200 within the hook budget for any request body, including a malformed, empty or absent one, and shall not write terminal task status.
- (P2) When the `/ready` hook runs, the agent shall exec the agent CLI binary before returning 200, so that its pages are resident when the snapshot is captured.
- (P2) If a required `/ready` warm-up does not complete successfully, then the agent shall report not-ready (HTTP 503) rather than allow the snapshot to be taken.
- (P2) The `/ready` hook shall make no AWS API call, warm-up included.

### 4. Infra and IAM: conditional resources behind bootstrap `ComputeTypes`

The infrastructure mirrors the ECS pattern. A `compute-lambda-microvm` bootstrap policy (`cdk/src/bootstrap/policies/`) is gated on the `ComputeTypes` CFN parameter. A CDK construct provisions the build role, the execution role (admitted to the per-session role through `AgentSessionRole.admitComputeRole`, which was designed for this case), the S3 artifact bucket wiring, and image build automation. Egress uses the platform VPC through egress network connectors, so the DNS Firewall, security-group, and flow-log stack in [COMPUTE.md](/sample-autonomous-cloud-coding-agents/architecture/compute) applies unchanged. Ingress is suppressed with the Lambda-managed `NO_INGRESS` connector. There is no `SHELL_INGRESS`, which is noted as a candidate for [#391](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/391) (operator session access) as a separate decision.

The construct has to encode two networking facts, both established live:

- **A `VPC_EGRESS` connector requires an operator role.** CloudFormation's generated L1 types `operatorRole` as optional, and this ADR originally assumed that Lambda would manage the ENIs with its own service-linked role. It does not. The connector fails to create with *"NetworkConnectorOperatorRole is required for VPC_EGRESS connector type"*. The construct creates one role. The role trusts the bare `lambda.amazonaws.com` service principal (see the trust-policy fact below) and carries `AWSLambdaVPCAccessExecutionRole` plus the ENI, tag, and private-IP actions that the managed policy omits. Both connectors share the role, because it manages interfaces, not traffic.
- **The MicroVM-facing roles cannot carry a confused-deputy source condition.** All three (build, execution, connector operator) trust the bare `lambda.amazonaws.com` service principal with **no** `aws:SourceAccount` or `aws:SourceArn`. That is a forced choice, not an oversight. The Lambda MicroVMs service presents no source key when it assumes them, so a trust policy that carries one cannot be assumed. The one cause had two symptoms, both live 2026-08-06/07 and both blocking:

  - Both `AWS::Lambda::NetworkConnector` resources `CREATE_FAILED` **deterministically**. The stack was freshly deleted, so the cause was not propagation lag. That matters, because *"The service is unable to assume the provided NetworkConnectorOperatorRole. Please verify the trust policy on the role."* is also the classic propagation symptom, and a re-run is the obvious wrong guess. After the condition was removed, both were created within a second.
  - `RunMicrovm` failed with a **misleading `iam:PassRole` AccessDenied on the caller**, with the orchestrator's grant present, `simulate-principal-policy` returning `allowed`, no permissions boundary, and a temporary *unconditioned* `iam:PassRole` **also** denied. The real cause was the execution role's trust. Removing its conditions made the next submission reach `RUNNING` in 6 s. The service therefore reports a role that it cannot pass and assume as an identity-policy denial on the principal that passes it.

  This is recorded because the fix looks like a regression to anyone who applies the standard service-principal pattern, and because it *was* a regression in the other direction. P1's standalone-validated operator-role probe had no conditions and worked, and the P1 F2 fix then added them "to mirror the build/execution roles". `sts:TagSession` stays, because the service needs both actions and it was never implicated.

- **Neither can the `iam:PassRole` grants carry an `iam:PassedToService` condition. The root cause is the same, on the identity side (P2r2-F9 and P2r2-F10, live 2026-08-07 run 2).** An earlier revision of this ADR recorded the opposite, that the identity-side condition "was exonerated" by run 1's elimination. **That was a false negative**, and its cause is recorded because it is a general trap. Run 1 tested the conditioned grant by *adding* a temporary unconditioned `iam:PassRole` and watching the task still fail. The temporary grant remained attached through the later submissions that succeeded, so the conditioned grant was never once tested against a working trust policy. The control was contaminated.

  Run 2 ran the clean experiment, with the same exact-ARN resource, the same ~5-minute IAM settle, and one variable. It removed the run-1 workaround **first** (submission 4: denied) and only then added the unconditioned grant back on the same resource (submission 5: `RUNNING`). Run 1 got that ordering wrong:

  | Orchestrator `iam:PassRole` on the execution role | Result |
  |---|---|
  | exact ARN **+ `iam:PassedToService: lambda.amazonaws.com`** | **DENIED** (two independent submissions) |
  | exact ARN, **no condition** | **`RUNNING` in 9 s** |

  The denial is reported on the **caller**, and that makes it misleading, because the statement names that exact ARN and `simulate-principal-policy` answers `allowed`:

  ```
  User: arn:aws:sts::<account>:assumed-role/backgroundagent-dev-TaskOrchestratorOrchestratorFn-…
  is not authorized to perform: iam:PassRole on resource:
  arn:aws:iam::<account>:role/backgroundagent-dev-LambdaMicrovmComputeExecutionRo-…
  because no identity-based policy allows the iam:PassRole action
  ```

  The same key blocks the *other* PassRole path, which run 1 never reached because the enum defect (P2-F2) stopped it earlier. CloudFormation could not pass the **build role** at `CreateMicrovmImage` under the bootstrap `infrastructure` policy's allowlisted `IAMPassRole`. The error is quoted verbatim, so that the diagnosis does not have to be taken on trust:

  ```
  LambdaMicrovmComputeImage…  CREATE_FAILED
  User: arn:aws:sts::<account>:assumed-role/cdk-hnb659fds-cfn-exec-role-<account>-us-east-1/AWSCloudFormation
  is not authorized to perform: iam:PassRole on resource:
  arn:aws:iam::<account>:role/backgroundagent-dev-LambdaMicrovmComputeBuildRoleF0-…
  because no identity-based policy allows the iam:PassRole action
  (Service: LambdaMicrovms, Status Code: 403)
  ```

  Three pieces of evidence attribute the denial to the *condition*, and not to a stale bootstrap or a wrong resource pattern:

  1. The live `IaCRole-ABCA-Infrastructure` policy was byte-identical to this branch's `cdk/bootstrap/policies/infrastructure.json`, so `cdk bootstrap --force` would have changed nothing.
  2. `aws iam simulate-principal-policy --policy-source-arn <cfn-exec-role> --action-names iam:PassRole --resource-arns <build-role-arn>` returned `allowed` **with** `--context-entries ContextKeyName=iam:PassedToService,ContextKeyValues=lambda.amazonaws.com,ContextKeyType=string` and `implicitDeny` with no context entry. The resource pattern therefore matches, and the condition key is the only remaining variable.
  3. The **control**. The out-of-band `create-microvm-image` call passed the *same build role* to the *same service* successfully, with operator credentials that carry no such condition. The role's trust is therefore fine, and the denial is caller-side.

  The conclusion is that **the Lambda MicroVMs service presents no usable value for `iam:PassedToService` on either PassRole path** (CloudFormation → build role at `CreateMicrovmImage`, and orchestrator → execution role at `RunMicrovm`), exactly as it presents no `aws:SourceAccount` on the assume-role path. This is one root cause with two more symptoms. Both statements therefore drop the condition, and the fix is deliberately asymmetric so that it stays contained:

  - `task-orchestrator.ts` sid `MicrovmPassExecutionRole`. The condition is removed. The **exact execution-role ARN** is now the whole of the scoping, so that resource must never be relaxed to a prefix or `*`.
  - A new sid `MicrovmPassRoles` in the **conditional** `compute-lambda-microvm` bootstrap policy. It grants unconditioned `iam:PassRole` on the build and connector-operator role **name prefixes only** (not the execution role, which CloudFormation never passes). The shared `infrastructure` `IAMPassRole` keeps its allowlist, so no other role in the stack loses that constraint, and an agentcore-only bootstrap never gains an unconditioned pass at all. **Operators must re-bootstrap** (bundle ≥ 1.6.0) for the CDK-managed image path to work.

  If AWS documents the value that the service does present, adding it to both statements restores the condition. `microvms.lambda.amazonaws.com`, `lambda-microvms.amazonaws.com` and `microvms.amazonaws.com` were all `implicitDeny` against the conditioned policy, so any one of them would serve as the allowlist entry if it turns out to be right. Note that CloudTrail carries **no `lambda-microvms` management events at all** today, so the value cannot be read out of a log. It can only be confirmed by AWS or found by a bounded sweep.

  The compensating controls are enumerated per role. The deployment-role's shared `IAMPassRole` grant is **name-prefix-scoped**, so it technically covers all three roles. In practice only the orchestrator invokes `iam:PassRole` on the execution role (CloudFormation never requests it). The other two roles are passed **to** the deployment role (not to themselves).

  | Role | Who can pass it, and how that grant is scoped |
  |---|---|
  | **Execution role** | The **orchestrator Lambda only**, at `RunMicrovm`. `iam:PassRole` is scoped to this role's **exact ARN**, with no condition (`constructs/task-orchestrator.ts`, sid `MicrovmPassExecutionRole`). The authoritative two-arm experiment evidence that the condition is the true blocker (not a permissions gap or stale bootstrap) is finding P2r2-F10 in `docs/verification/645-p2-smoke-runbook.md`. The comment on that statement cites the finding. |
  | **Build role** | The **CloudFormation deployment role**, at `CreateMicrovmImage` (the L1's `buildRoleArn`), through the new `MicrovmPassRoles` statement, scoped to `role/backgroundagent-dev-LambdaMicrovmComputeBuild*`, with no condition. Also whoever runs `package-microvm-artifact.sh --create-image` out of band, with their own credentials. |
  | **Connector operator role** | The **CloudFormation deployment role**, at `AWS::Lambda::NetworkConnector` create or update (`operatorRole`), through the same statement, scoped to `role/backgroundagent-dev-LambdaMicrovmComputeConnector*`. |

  The rest of the posture is as follows. Every resource that these roles can reach is account-scoped by ARN, **except two deliberate `Resource: '*'` statements**. The first is `ec2:DescribeAvailabilityZones` on the execution role. EC2 describe actions have no resource-level scoping. The action is read-only, with no mutation and no data access, and it is needed so that a CDK target repo's `cdk synth` build gate can resolve AZ context on a fresh clone. The second is the connector operator role's ENI, tag, and private-IP statement. `CreateNetworkInterface` is authorized before the ENI exists and the `Describe*` calls take no resource, and for the same reason the AWS-managed VPC-access policy uses `*` too. Both are justified in the construct's cdk-nag `AwsSolutions-IAM5` suppressions, and a reviewer should check them there, not here. The Logs grants are prefix-scoped (`/aws/lambda-microvms/*` plus one named log group), that is, wildcards inside a namespace, not `*`. Separately, the **orchestrator's** `lambda:PassNetworkConnector` is also `Resource: '*'`, unavoidably. The AWS-managed connectors are in the `aws` account, outside any ARN that we could enumerate (justified in `task-orchestrator.ts`, sid `MicrovmPassNetworkConnector`). Finally, none of the three roles holds `iam:*`, none has cross-account trust, and the only `sts:AssumeRole` that any of them has is the execution role's, scoped to the per-task SessionRole.

  If AWS later populates a source key on this path, adding it to the shared principal fixes all three roles and both `sts` actions at once.

- **Build-time egress needs port 80, and runtime does not.** `agent/Dockerfile` installs Debian packages and `apt-get` fetches over plain HTTP, so a 443-only egress path fails every snapshot build (`Could not connect to deb.debian.org:80 … exit code: 100`). Instead of widening the runtime posture, the construct provisions a **second, build-only** connector on the same private subnets with a security group for 443 and 80. Only the image resource and the packaging script reference that connector. The agent at run time still has 443-only egress.

- Where the bootstrap `ComputeTypes` parameter includes `lambda-microvm`, the generated template shall attach the `IaCRole-ABCA-Compute-LambdaMicrovms` policy to the CloudFormation execution role.
- The orchestrator role shall receive only the MicroVM lifecycle actions it calls (`lambda:RunMicrovm`, `lambda:SuspendMicrovm`, `lambda:ResumeMicrovm`, `lambda:TerminateMicrovm`, `lambda:GetMicrovm` for `pollSession`, and `lambda:PassNetworkConnector`, which is required even for the default connectors), scoped to platform-created images.
- Where the `lambda-microvm` backend is enabled, the approve and deny Lambdas shall receive `lambda:ResumeMicrovm` and `lambda:GetMicrovm`, conditionally, mirroring the cancel handler's conditional `RUNTIME_ARN` wiring in `task-api.ts`.
- The trust policy of every MicroVM-facing role shall name `lambda.amazonaws.com` and shall carry no source-condition key (the service presents none, see the trust-policy fact above).
- The `iam:PassRole` grant the orchestrator uses for the MicroVM execution role shall carry no `iam:PassedToService` condition and shall be scoped to that role's exact ARN.
- Where the bootstrap `ComputeTypes` parameter includes `lambda-microvm`, the `IaCRole-ABCA-Compute-LambdaMicrovms` policy shall grant `iam:PassRole` without an `iam:PassedToService` condition, scoped to the MicroVM build- and connector-operator role name prefixes, and shall not extend that grant to the MicroVM execution role.
- The shared `IaCRole-ABCA-Infrastructure` `iam:PassRole` statement shall retain its `iam:PassedToService` allowlist.
- The MicroVM execution role shall hold `logs:CreateLogStream` and `logs:PutLogEvents` on the application log group whose name is delivered in `platform_config`, scoped to that log group.

`lambda:CreateMicrovmAuthToken` is granted to no role in P1–P3 (no JWE consumer exists, see sub-decision 3).

**Cost attribution update (#852).** The `compute_types` context selects an ordered backend list. Legacy `compute_type` retains its additive meaning. The stack-level `compute_type` tag records all deployed names separated by `+` (for example, `agentcore+lambda-microvm`), which is valid in AWS tag values. MicroVM-specific resources retain their `abca:compute-backend` tags. Shared optional services remain independent of the compute selection. An unchanged legacy context preserves AgentCore. Deliberate backend removal requires a drained transition (see [Compute](/sample-autonomous-cloud-coding-agents/architecture/compute#selecting-and-changing-the-backend)).

- Where a deployment enables the `lambda-microvm` backend, MicroVM-specific resources shall carry backend-identifying cost-allocation tags.

#### Regional availability enforcement

Lambda MicroVMs launched in 5 regions (us-east-1/2, us-west-2, eu-west-1, ap-northeast-1) and will expand. ABCA is a single-region deployment, so the constraint is binary per stack. Either the stack region supports the backend or the backend does not exist there. Enforcement is layered. One static check runs where offline determinism is required. Live probes run everywhere else, so the platform recognizes new regions as AWS adds them (`list-managed-microvm-images` is the documented read-only availability probe):

| Stage | Mechanism | Check |
|---|---|---|
| CDK synth/deploy | Static region constant (single exported list, documented update path) | Synth fails when `ComputeTypes` includes `lambda-microvm` in an unlisted region. A context flag overrides the check for newly launched regions ahead of the constant update |
| Repo onboarding | Live probe from the CLI | `bgagent repo onboard --compute-type lambda-microvm` calls `list-managed-microvm-images` in the stack region and rejects with a remedy (the supported-region list, and a suggestion of `agentcore` or `ecs`) |
| `bgagent platform doctor` | Live probe (precedent: `checkBedrockModel`) | Reports backend availability for the stack region whenever any active blueprint selects `lambda-microvm` |
| Orchestration (defense in depth) | Error classification | `startSession` failures from a missing regional endpoint classify to a typed remedy in `error-classifier.ts`, never a cryptic SDK error on the task |

- If an operator onboards a repo with `compute_type: 'lambda-microvm'` and the availability probe fails for the stack region, then the CLI shall reject the onboarding with the supported-region list and alternative backends as the remedy.
- If `startSession` fails because the MicroVM service is unavailable in the stack region, then the orchestrator shall classify the failure with a configuration remedy and shall not retry.
- When the platform doctor runs in a deployment where any active blueprint selects `lambda-microvm`, the doctor shall probe MicroVM availability in the stack region and report the result.

### 5. Rollout: phased, default unchanged

- **P1: strategy, infra, and minimal hook serving.** `LambdaMicrovmComputeStrategy` (start/poll/stop), CDK construct, bootstrap policy, types sync, unit and CDK assertion tests, and the agent's `/ready` and `/run` endpoints. No suspend yet. The image IS creatable and launchable and the payload DOES reach the agent, but there is **no smoke-parity guarantee** (sub-decision 3's phasing table).
- **P2: smoke parity.** The agent serves `/terminate` and `/validate` and installs its platform env from the `/run` payload (see sub-decision 3's "Platform configuration delivery"). The agent completes the clone, change, and PR flow on the backend with progress visible to `bgagent watch`. Failure classification entries are added to `error-classifier.ts`. **AgentCore Memory parity** is added (IAM grant plus `MEMORY_ID` delivery, following the `EcsAgentCluster` pattern). Memory is a standalone service already consumed cross-substrate, and omitting the grant silently disables cross-session learning. The agent's remaining non-secret env parity inside the snapshot is completed.
- **P3: suspend and resume.** The interface widening from sub-decision 1 (mandatory methods, all three strategies in one commit), the HITL-wait suspend policy, inline resume in the approve and deny Lambdas with orchestrator-poll reconciliation (sub-decision 2), and timeout-under-freeze wall-clock handling. Coordinate with [#491](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/491)'s unified liveness model and update Cedar decision #7's rationale note.
- **Out of scope.** Replacing AgentCore as default, classic Lambda functions as a runtime, GPU, and the Runtime-coupled workload-access-token injection path. The delivery mechanism for that path exists only on AgentCore Runtime, and MicroVMs adopt the ECS env-var posture until [#249](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/249) and ADR-016 redesign the seam. Gateway integration is orthogonal. ADR-019 ([#641](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/641)) is substrate-portable by design and applies to this backend when it lands.

### P3 as delivered

P3 implements sub-decisions 1 and 2 as written: mandatory `suspendSession` and `resumeSession` on every strategy (AgentCore and ECS return `{ supported: false }`), an orchestrator-owned suspend policy for HITL waits, inline best-effort resume in `ApproveTaskFn` and `DenyTaskFn` with a `microvm_resume_orphan` event and orchestrator-poll reconciliation, the `min(monotonic budget, created_at + timeout_s)` gate deadline, and agent `/suspend` and `/resume` hooks that flush progress, reseed CSPRNGs and refresh credentials. Approval windows stay **bounded** (Cedar decision #6: default 300 s, floor 30 s, ceiling 3,600 s), so a suspended worker always outlives its gate and no worker replacement is needed. Implementation found five facts that refine the design:

- **A non-200 `/suspend` answer terminates the MicroVM.** The service does not retry and does not leave the VM running (verified live: state reason "Suspend lifecycle hook returned HTTP status 409"). The guest therefore *declines* an unsafe suspend with 200 `declined` and keeps its coding barrier open. The VM freezes with memory intact and the coordinator wakes it, and the following `/resume` answers 200 `not-suspended`. Non-200 remains only where nothing is left to protect (no registered task, or a barrier permanently closed by a failed wake or teardown) and for a failed `/resume` after an acknowledged suspend.
- **Credential renewal needs a synchronous barrier.** The pinned Claude CLI returns its previous cached `awsCredentialExport` value while it refreshes in the background, which is not an acknowledged refresh after a freeze. MicroVM workers leave that export empty and give the CLI a loopback container-credential provider (`microvm_credentials.ScopedCredentialBroker`) that renews before signing a request with expired keys. `/resume` refreshes the task-scoped and ambient credentials before the barrier opens. Model calls fail fast (`API_TIMEOUT_MS`) because sockets idle across a suspend can be dropped silently.
- **Suspension is gated on the launched image, not the deployment.** The coordinator records the actual `imageArn` and `imageVersion` returned by `RunMicrovm` and verifies the image version's declared lifecycle protocol (`ABCA_MICROVM_LIFECYCLE_PROTOCOL`, all six hooks) before allowing sleep. A legacy or unverified image keeps running and can still be woken.
- **Suspension has a live off-switch and a per-task delay.** `microvm_approval_suspend_enabled` (default false) creates a Parameter Store switch that the supervisor reads before each suspend, so pinned durable executions can stop new suspensions without redeploying. Turning the switch off never abandons a suspended worker. A task's `microvm_sleep_after_s` (CLI `--microvm-sleep-after`, `off` = 0) is captured at submission. The default is 60 s, so that a default 300 s gate sleeps. The grace ends at 60 s, and the worker wakes `MICROVM_WAKE_MARGIN_MS` (60 s) before the original deadline, that is, at 240 s. The supervisor never suspends for less than 30 s.
- **MicroVM resources live in a nested stack.** `microvm_nested_stack` must be selected explicitly (`true` for new and already-nested deployments, `false` to keep an existing flat installation) because moving a flat deployment's resources is not a safe migration (see [645-p3-nested-stack.md](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/blob/main/docs/verification/645-p3-nested-stack.md)). Bootstrap 1.9.0 or later covers the nested role names. Stateless scheduled maintenance (concurrency and stranded reconcilers, admission pickup, upload cleanup) is also nested to keep every backend profile inside the 490-resource root budget ([ADR-023](/sample-autonomous-cloud-coding-agents/decisions/adr-023-cloudformation-stack-boundaries)).

**Follow-ups, not in P3.** Each needs its own approved issue: recovering a task on a replacement worker when its suspended worker is lost (compute-agnostic continuation), approval waits without an automatic deadline, a trusted approval-writer API that removes workers' direct approvals-table writes, Linear approve and deny replies, IAM-authenticated payload bootstrap with signed per-task URLs, and a capacity-reservation rewrite.

## Consequences

- (+) **Suspend/resume economics.** Tasks that idle on approval waits stop billing compute and keep full state. The saving is bounded at ~1 h per gate under the current Cedar ceiling (decision #6), and it makes off-hours gate-ceiling extensions cheap later (§14.8). Verified end to end at the substrate level: suspend and resume each complete in ~1 s, and `microvmId` **and** `endpoint` survive the cycle byte-identical, so a stored `SessionHandle` remains valid.
- (+) **VM-level isolation without cluster ops.** Firecracker isolation with no ECS cluster, task definition, or capacity management. One session per MicroVM maps one to one onto ABCA's task model.
- (+) **Avoids AgentCore's 2 GB image limit and FUSE `flock()` workaround.** Native disk in the snapshot supports `uv` and `mise` without the split-storage scheme. The size comparison must say WHICH measure it means. The same agent tree is 1.799 GB as an OCI image (629.7 MB compressed, which is under AgentCore's limit) but reports `codeInstallSizeInBytes` of 2.17 GiB as a MicroVM snapshot (which is over it). The two measures fall on opposite sides of the limit and are not interchangeable. Memory and disk snapshot sizes are a third measure and must not be summed into the comparison.
- (+) **Liveness becomes explicit.** Unlike AgentCore's stub `pollSession`, the strategy can report real substrate state, which strengthens the [#491](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/491) unification.
- (−) **32 GiB sustained ceiling (8 GiB baseline + automatic 4× vertical scaling), 32 GB disk.** The backend is not a successor to the ECS backend for heavy CI-parity builds. The platform now maintains three backends.
- (−) **Capacity is baseline-priced with burst headroom, which is a narrower promise than "32 GiB".** The deployment configures an 8 GiB / 4 vCPU baseline and the service scales to 32 GiB / 16 vCPU on demand. That shape matches an agent task, which is mostly idle while it waits on the model and spiky during builds, and it is cheaper than reserving the peak. But it is *burst*, not a reservation. A workload that needs 32 GiB **sustained** relies on scaling behaviour that this ADR has not measured, and against ECS's 120 GB the gap for sustained-memory workloads is unchanged. The value therefore remains the suspend economics, the observable control-plane state machine, and the absence of cluster ops. Capacity is now a fair-to-good fit, not a hard blocker. Repos with sustained heavy builds still belong on `ecs`.
- (−) **New packaging pipeline.** Zip, Dockerfile, and service-side image builds with versioned snapshots (storage billed per version) run alongside the existing ECR flow. Image versions need lifecycle cleanup, including versions left behind by FAILED builds. The last version of an image cannot be deleted individually (delete the image, which reaps it).
- (−) **The payload bucket is on the hot path, not the overflow path.** With a 4 KB `runHookPayload` cap, almost every real task delivers its payload through S3, so the bucket, its TTL rule and the execution role's read grant are required for normal operation, not an edge case (sub-decision 3).
- (−) **8-hour hard cap includes suspended time**, and with `idlePolicy` omitted there is no tighter substrate-level suspended-TTL. The suspended-state bound is `maximumDurationInSeconds` plus orchestrator termination and the stranded reconciler. A manually suspended VM was observed alive at 1 h with no TTL reached (the observation was truncated there), so nothing contradicts this bound, but nothing narrows it either. Under today's 1 h gate ceiling the bound is sufficient. Any future extension of gate ceilings must revisit the bound (an additive `idlePolicy` change) and give the orchestrator a checkpoint-and-restart path (push branch, new session) beyond the cap.
- (!) **Idle-policy hazard.** Traffic-based auto-suspend would freeze a busy outbound-only agent. The decision to disable auto-suspend must be enforced in code and covered by tests, not left to configuration discipline.
- (!) **Service defaults are not the desired posture.** Two cases caught live (public `HTTP_INGRESS` by default, and `/ready` mandatory) show that an omitted field on this backend does not mean "off". It can mean "the service picks, and it picks wider than we want". Assume that every new `RunMicrovm` or `CreateMicrovmImage` field has an opinionated default until it is checked.
- (!) **Nothing self-terminates on the paths that matter.** This bullet supersedes P1's unqualified version. With `run: ENABLED` the service DOES reap a VM whose run hook returns 4xx (~12 s, `stateReason: "Run lifecycle hook returned HTTP status 400."`, live-verified), so a guest that rejects its own payload cleans itself up. That is the only self-cleaning case. The service reaps a hook *result*, and once `/run` has answered 200 it has no view of the guest. A VM whose task finished, crashed after `/run`, or hung stays `RUNNING` and bills until the 8 h cap. The orchestrator's `TerminateMicrovm` on finalize therefore remains the only cleanup for normal operation, and a leaked handle is still a cost incident.
- (!) **Snapshot uniqueness.** Shared memory snapshots mean that every MicroVM restored from one image starts with identical PRNG state. **Re-scoped to P3 in the P2 review, with the exposure measured, not assumed** (see the amendment under sub-decision 2). The sole `random` consumer in `agent/src` is a ULID sort key under a `task_id` partition, `os.urandom` and `secrets` are unaffected, and no credential or token derives from `random`. The P2 exposure is therefore a possible duplicate progress event, not a security boundary. The reseed becomes necessary at P3, where a *resumed* VM continues from frozen state repeatedly. The reseed must land on `/run` and `/resume` together with those hooks. Asserting the requirement while leaving it unimplemented was the real defect, and this amendment is the fix.
- (−) **The agent stack template is at 98.6 % of CloudFormation's 1 MB limit** (985,886 bytes) and at 486 of 500 resources with a MicroVM image configured. That leaves ~14 KB of headroom, roughly one more construct. One run earlier the template was at 98.4 % with ~16 KB of headroom. This backend did not cause the problem (the MicroVM construct is ~6 KB of the template) but it brought the template to this point, and the limit will block deploys for reasons that have nothing to do with MicroVMs. Tracked in [#735](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/735). The candidate remedies are `suppressTemplateIndentation` and a stack split.
- (!) **Snapshot WARMTH is a required property, not an optimisation.** A snapshot inherits only the pages that something touched before it was captured. A large lazily loaded artifact, such as the 225 MiB `claude` binary or anything similar added later, therefore pays its first-touch cost on the *first task* instead of at container start. That cost failed every task at turn 0 in the P2 smoke run (P2-F5). Anything heavyweight added to the image must be exec'd in `/ready`, and any timeout that guards a first touch must be sized for a cold page fault, not for the work itself.
- (!) **Regional availability (5 regions at launch, expanding).** Enforced in layers (synth-time static check, onboarding and doctor live probes, orchestration-time classification, see sub-decision 4). The static CDK constant is the one piece that goes stale as AWS expands. Its update path and context-flag override are deliberate.
- (!) **Workload-token injection delta persists** (shared with the ECS backend) until [#249](https://github.com/aws-samples/sample-autonomous-cloud-coding-agents/issues/249) and ADR-016 land. Document it in the security bar comparison and do not block on it. Memory and Gateway are explicitly *not* deltas. Both are standalone services consumed through IAM from any substrate.

## Testing

**P1 (start/poll/stop, no suspend):**

- Unit tests for the strategy: start/poll/stop mapping (including `SessionStatus` `'suspended'` reported mechanically, without task-state interpretation), payload-size branching (inline or S3 pointer, at the exact 4 096/4 097-byte boundary), the image-identifier-must-be-an-ARN guard, the explicit `NO_INGRESS` argument (including the blank-env-var fallback, which must never omit the field), error classification (`ServiceQuotaExceededException`, `ThrottlingException`, `ResourceNotFoundException`, regional-unavailability), the omit-`idlePolicy` invariant, and `maximumDurationInSeconds` fixed at 28 800.
- Agent tests: `/ready` returns 200 once the server is up and starts nothing. `/run` accepts both envelope shapes (inline and S3 pointer), starts the pipeline asynchronously through the same mapper that `/invocations` uses, returns before the pipeline finishes, and rejects every unusable envelope with a named code before spawning. `/suspend` and `/resume` are NOT served (`/validate` and `/terminate` joined the served set in P2).
- Orchestrator tests: a terminal substrate state with a non-terminal task status is classified as failed. `suspended` with a status other than `AWAITING_APPROVAL` produces an anomaly event and no fail-fast. `compute_metadata` is persisted with `microvmId` and `endpoint` after `startSession`.
- CDK assertions: MicroVM resources present only when `ComputeTypes` includes the backend, synth failure for unsupported regions (plus the context-flag override), memory size validated against the accepted list at synth, the connector operator role and its trust, two connectors of which the build-only one carries port 80 and the runtime one does not, the `/ready` and `/run` hook declaration and the absence of the others, IAM actions scoped as specified (the orchestrator lifecycle set, and no `CreateMicrovmAuthToken` anywhere), payload-bucket grants (execution role read-only), backend cost-allocation tags, and a types-sync check that covers the widened `ComputeType`.
- CLI tests: onboarding rejection with remedy when the availability probe fails, and a doctor check present when a blueprint selects the backend.
- P1 verification items (external service facts), **executed 2026-07-31, us-east-1**. See `docs/verification/645-p1-lambda-microvm-runbook.md` for the full evidence. Discharged: `runHookPayload` limit (**4 096**, not 16 KB), the accepted baseline memory sizes (`[512…8192]` MiB, where the developer guide, not the probe, establishes that this is a BASELINE with a 32 GiB peak), image-identifier ARN requirement, IAM action names and the observed image-ARN shape, region probe behaviour, manual suspend and resume without `idlePolicy`, terminate timing and the `TERMINATED`-persists-≥10-min finding, the default public `HTTP_INGRESS`, and the `/ready` requirement. **Not** discharged: account-quota treatment of `SUSPENDED` MicroVMs (not observable safely), suspended TTL beyond 1 h (truncated), the vertical-scaling behaviour itself (no workload here approached the baseline, so the 4× peak is documented, not observed), and the `AWS::Lambda::MicrovmImage` CloudFormation value shapes (never exercised, because the run used the out-of-band script path. **Discharged, and REFUTED, by the P2 run, see P2-F2 in sub-decision 3**). Record the closed answers in COMPUTE.md.

**P2 (smoke parity):**

- Agent tests: `/validate` returns 200 with its individual check results, returns 503 while initialising, reports a missing hook route or an unsupported interpreter, starts nothing, and makes **zero AWS calls even with `LOG_GROUP_NAME` set** (asserted by poisoning the boto3 and CloudWatch-writer seams, and the same assertion covers `/ready`). `/terminate` returns 200 with no body at all, with a malformed, non-object, wrong-content-type, or whitespace-only body, when the body read itself fails, with a pipeline still running (without joining it), and when its own best-effort step raises. It never calls `task_state.write_terminal`. A structural assertion that the route carries no typed body param keeps the 422 from being reintroduced.
- `platform_config` tests: the allowlist and required subset are read from `contracts/constants.json` (the wire key set is also asserted literally, so that a contract edit fails an agent-side test). An unknown key rejects the whole block with nothing installed. A non-object block and a non-string value are rejected. A blank or `null` optional value is skipped without overwriting an image value, while a blank required value is rejected. A payload value beats a pre-existing env value. Installation is observed to happen before the GitHub-token resolver runs and before any pipeline thread exists. The config is picked up from the inline envelope, from beside the S3 pointer, and from inside the fetched object (inner wins). An envelope with no `platform_config` is still accepted with a warning.
- Snapshot credential hygiene: a subprocess probe asserts that importing `server` and serving `/ready` and `/validate` imports neither `boto3` nor `botocore`, caches no `aws_session` session, and spawns no CloudWatch writer thread. That property keeps a build-role credential chain out of the snapshot (region is re-resolved per client, so it is not frozen).
- `/run` pre-install silence: with a **baked `LOG_GROUP_NAME`** (the hostile case, because without it the assertions pass vacuously) every AWS and credential seam (`boto3.client`/`Session`, the `aws_session` factories, `_debug_cw`/`_warn_cw`) is armed to raise until the install succeeds. This is asserted on the accepted path, on all three rejection paths (bad envelope, `platform_config` invalid, `platform_config` incomplete) and on the failed-fetch 500, where the seams stay armed for the whole request because a rejected run installed nothing and so is allowed no AWS call. The permitted exception is asserted POSITIVELY: exactly one client is built pre-install, for `s3`, through the attributed factory.
- `/ready` warm-up tests (P2-F5): the hook exec's each configured binary exactly once with a generous timeout. `claude` is the only REQUIRED entry. A timeout, a missing binary, a non-zero exit and an unexpected `OSError` each produce **503 with the reason logged to stdout**, not a 200 or a 500. A best-effort failure still reports ready. The warm-up makes zero AWS calls with `LOG_GROUP_NAME` baked. The backstop half is also tested: the `claude --version` probe's bound is asserted to be ≥ 60 s and to be applied to the *exec*, not to the PATH lookup, and a missing CLI warns instead of raising.
- CDK assertions (P2-F1/F2/F4): no source-condition key on any of the three MicroVM-facing role trusts, and no `aws:SourceAccount`/`aws:SourceArn` string anywhere in them. Hook properties are `ENABLED` and the architecture is `ARM_64`, with a negative assertion that **no** hook route string appears anywhere in the rendered image resource. The agent hook routes are asserted against their own dedicated constant (the template no longer carries a path to compare). The execution role holds `logs:CreateLogStream`/`PutLogEvents` on the application log group and the two logs grants stay separate. The stack wires the SAME log group that it delivers as `platform_config.log_group_name`.
- Smoke (gated like the ECS backend): clone → change → PR with `bgagent watch` progress, and Memory write parity (no AccessDenied no-op). **Run 1 (2026-08-06) FAILED at `implement`, turn 0, with no PR. Run 2 (2026-08-07) PASSED: two tasks clone → change → commit → push → PR, `COMPLETED`, 12 turns / $0.279 / 153 s** (`docs/verification/645-p2-smoke-runbook.md`). Run 2 also discharged P2-F1, P2-F2, P2-F4, P2-F5 and the dual-signal-liveness item (45 s heartbeat cadence observed across a 181 s `RUNNING` window). **The row is not yet fully closed.** Run 2 needed one live IAM workaround, and establishing why produced P2r2-F10 (the identity-side `iam:PassedToService`) and P2r2-F9 (its CloudFormation twin). Both are fixed in source above and neither has been re-exercised live, so what remains is a re-run on a re-bootstrapped account with no workarounds.

**P3 (suspend/resume):**

- Unit tests: suspend and resume mapping, agentcore and ecs `unsupported` stubs, and approve and deny inline resume with the handle loaded from `compute_metadata`.
- HITL lifecycle tests: an inline resume failure leaves the decision outcome intact and records the orphan event. The orchestrator backstop retries resume. Gate expiry fires at `min(monotonic budget, created_at + timeout_s)`, including the suspend and resume case where the monotonic budget exceeds the wall-clock remainder, without disturbing the §13.12 late-approval race protection.
- Smoke: suspend/resume across a simulated approval wait preserving workspace state.
